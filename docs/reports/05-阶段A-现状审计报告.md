### 1.3 数据实体与存储实现

| 实体 | 字段 | 存储 |
|---|---|---|
| `Raw` | id / text（≤50000）/ createdAt | `data/raw.json` |
| `Knowledge` | id / rawId / title / summary / content / keyPoints[] / concepts[] / keywords[] / createdAt / updatedAt | `data/knowledge.json` |
| `KnowledgeRelation` | id / sourceId / targetId / **type 恒为 `"related"`** / reason / createdAt | `data/relations.json` |
| `OrganizeDraft` | 同上 + `relatedKnowledge[]` | **不持久化**（服务端返回的临时结构）|

**存储实现细节（重要）**：4 个 `*-storage.ts` 都用 `node:fs/promises` 读写 `path.join(process.cwd(), "data", "*.json")`。

- 读取：文件不存在（`ENOENT`）时返回空数组，不抛异常。
- 写入：**每个模块自带一个 `writeChain` 队列**，把同一进程内的写操作串行化——所以单个实例内并发写不会互相覆盖。
- 但 `writeFile` 是**非原子**的（先读全量 → 改内存 → 覆盖整个文件），写入过程崩溃可能损坏文件，且没有事务。

## 二、按约定口径分类

### A. 已实现的能力

1. Raw 的创建 / 列表 / 删除（含 50000 字长度校验、被引用时 409）。
2. AI 整理：调 DeepSeek 生成结构化 Draft，服务端做形状校验并过滤不存在的关联建议。
3. 审阅入库：Draft 逐项可编辑 → 用户确认 → Knowledge，且重复确认幂等。
4. Knowledge 内联编辑（标题 / 摘要 / 正文 / 概念），走 `PATCH` + 白名单字段校验。

6. 反向链接**接口**（动态查询，不落表）与图谱**接口**（实时派生 nodes/edges）。
7. 单页工作台：文件树 + 标签页 + 面包屑 + 右栏 AI + 移动端导航。
8. 首屏落地页（滚轮/触摸/键盘揭示 + Three.js 水晶 + WebGL 降级海报）与界面音效。
9. 统一的错误响应结构与"发生了什么 / 数据是否安全 / 下一步"式文案。

## 三、数据库与部署兼容性评估（按实际文档核实）

> 本节每条结论都基于 2026-10-10 抓取的 `docs.netlify.com` 实际页面。页面标注的最后更新时间：Netlify Database 概览 2026-06-16，Next.js on Netlify 2026-02-04。

### 3.1 核实到的事实

**① 本项目在 Netlify 上如何运行**

Netlify 通过开源的 **OpenNext 适配器**零配置支持 Next.js。它会：

- 为 SSR、ISR、**Route Handlers / API 路由**、Server Actions 提供一个 **serverless Netlify Function**；
- 为 Middleware 提供一个 **Edge Function**；
- 用 Netlify Image CDN 承接 `next/image`；
- 支持 App Router、SSR、ISR、SSG、Server Actions、Streaming、Route Handlers、重定向重写等。

**② 因此有两处限制直接影响本项目**

- **函数环境是临时的、按流量横向扩容**（Functions 文档原文："runs it in an ephemeral runtime environment... automatically scales according to the volume of traffic"）。→ **写本地文件既不是持久化、也不跨实例共享**。
- **Node.js Middleware 不支持 Filesystem**（Next.js 文档 Limitations 原文）。→ 如果将来把访问口令放在 middleware 里，只能用 Cookie/Header 判断，**不能读文件**。

**③ Netlify 确实有内置 Postgres，但有两个前提**

Netlify Database 是"内置于平台的完全托管 Postgres"，特点是：

- **仅 credit-based 计划可用**，数据库活跃时消耗 credits（compute 与 bandwidth）；页面写明"database storage space is free until July 1, 2026"。
- 生产部署才能访问主库；Deploy Preview 会拿到**独立的数据库分支**（创建时复制生产数据）。

**④ 接入方式（很关键，决定改造量）**

官方推荐包是 **`@netlify/database`**，它提供：

| API | 用途 |
|---|---|
| `getConnectionString()` | 返回当前环境的 Postgres 连接串（自动指向正确的数据库分支），**可以用你自己的驱动或 ORM** |
| `getDatabase()` | 返回已按运行环境优化的数据库客户端（build / 长驻服务 / Functions / Edge 各自选最合适的连接方式）|
| `db.sql` | 标签模板函数，插值自动参数化（防注入），基于 Waddler；支持 `execute/stream/chunked/toSQL` |
| `db.pool` | 标准 `pg.Pool`，**用于事务**（BEGIN/COMMIT/ROLLBACK 需同一连接）|

也可以直接用 `pg` + `getConnectionString()`。**这与"标准 Postgres"是兼容的**——意味着换供应商的迁移成本不高，这是降低供应商绑定的重要事实。

**⑤ 迁移机制**

- 迁移文件放在 **`netlify/database/migrations/`**，由平台在部署生命周期中**自动应用**；
- `netlify database init` 可交互式初始化（装包 / 选 Drizzle 或直接 SQL / 生成首个迁移 / 可选种子数据）；
- **`netlify dev` 会在本机起一个本地 Postgres**，因此本地开发不碰生产库。

**⑥ 备份与恢复（这是好消息）**

Netlify 的 REST API 提供**数据库快照**能力：创建快照、列出快照、删除快照、**把快照还原到某个分支**（`POST /sites/{site_id}/database/snapshot`、`.../snapshot/{id}/restore`）。这正好可以满足项目文档对"备份、迁移、回滚和恢复"的要求。

**⑦ 另一个可选存储：Netlify Blobs**

Blobs 是可配置一致性模型的键值/非结构化存储（默认最终一致，可逐次读选择强一致；支持原子条件写）。官方明确说：如果要做复杂查询、并发控制或关系模型，应改用数据库。

→ **结论：Blobs 不适合作为本项目的权威数据源**，但**适合后续放附件、原图、OCR 中间产物**。

### 3.2 四条路线对比

| 路线 | 改动量 | 持久化 | 事务 | 迁移 | 备份/恢复 | 费用 | 供应商绑定 |
|---|---|---|---|---|---|---|---|
| **① Netlify Database** | 中 | ✅ | ✅ | 平台自动应用仓库里的迁移 | ✅ 快照 + 还原 | ⚠️ **credit-based 计划** | 中（但出口是标准 Postgres + `getConnectionString`）|
| **② 外部 Postgres（如 Neon / Supabase 免费额度）** | 中 | ✅ | ✅ | 用 ORM 或自管迁移 | 看服务商 | 可能有免费额度 | 低（标准连接串）|
| **③ 换到有持久磁盘的宿主（Fly.io / Railway / Render）** | 小 | ✅ | SQLite 也有 | 自管 | 自管/备份文件 | 通常最低 | 低 |
| **④ 维持现状（本地 JSON 文件）** | 零 | ❌ 在 Netlify 上**不成立** | ❌ | ❌ | ❌ | 0 | — |

### 3.3 推荐

**推荐路线 ①（Netlify Database），理由是它最贴合项目文档的要求**：平台托管 Postgres、迁移随部署自动应用、本地有独立 Postgres、有快照还原机制、连接入口是标准 Postgres 连接串（因此路线 ① 与 ② 之间迁移成本不高）。

**唯一的前提是 E1：它是 credit-based 计划的功能。** 如果校赛预算不能接受任何付费，那么走**路线 ②**（外部 Postgres 免费额度）能得到几乎相同的架构——因为接入层都用标准连接串 + 事务，业务代码不用改。我不建议为了省事继续走路线 ④，那会让项目文档要求的"云端持久化、多设备、用户隔离"全部落空。

**路线 ③ 是备选**：如果你们判断 Netlify 的平台约束（函数无状态、Serverless 冷启动、DB 需付费）不值得，换一个有持久磁盘的宿主，改动量反而更小——但会失去 Netlify 的自动迁移与快照。

### 3.4 迁移风险与回滚（初步）

| 风险 | 说明 | 应对 |
|---|---|---|
| 现有数据极少 | `data/` 只剩 `.gitkeep`，没有真实业务数据 | **迁移风险极低**，实际上是"从零建库"，不需要数据搬迁 |
| 路由行为回退 | 改成数据库实现后，10 个接口的行为必须完全不变 | 先做**双实现对照测试**（JSON 适配器 vs DB 适配器，同一输入断言同一输出）|
| 本地与生产差异 | 本地用 `netlify dev` 的本地 Postgres，生产用分支库 | 迁移脚本在两个环境各跑一次，均需通过 |
| 回滚 | 无历史版本可依赖 | 每次迁移前建**快照**；代码回滚 = 还原到上一个部署（Netlify 支持）|
| 密钥泄露 | 连接串包含凭据 | 只用平台注入的环境变量 / `getConnectionString()`，**绝不写进仓库**；日志中不打印连接串 |

## 五、本阶段结论与下一步

**结论**：产品功能骨架是健康的——闭环成立、校验认真、错误文案讲究、存储层有容错与写入串行化。但**面向"云端 + Agent 接入"的架构基本是空的**：没有服务层、没有归属与授权、没有数据库、没有版本与幂等、没有审计、没有文档契约、没有测试。这不是"补几个功能"，而是**补一层地基**。
