## 五、推荐方案与理由

**推荐：Neon 免费计划。**

1. **满足项目文档选择原则第 1、2 条**：不强制付费（无信用卡、无时间限制），且是与现有项目兼容的标准 PostgreSQL。
2. **被 Drizzle 官方支持**（有独立接入指南），符合"采用 Drizzle ORM"的既定方向；并提供**连接池**，这是 serverless 部署的必要条件。
3. **额度对校赛 Demo 有充足余量**（估算见下）。而且它正是 Netlify 内置数据库的底层引擎，将来若付费升级，架构不用重做。

### 5.1 额度余量估算（估算，非实测）

- 单条 `Raw` 上限 50000 字符；中文按 UTF-8 约 3 字节/字 → 约 **150 KB**（这是**上限**，真实笔记通常远小于此）。
- 1 GB ≈ 理论上可容纳约 **6800 条**"写满上限"的原始记录；加上 `Knowledge` 派生字段与索引开销，实际可用条目数依然远超校赛需要。
- 计算侧：100 CU-hours/月，演示场景查询稀疏且闲置 5 分钟即缩容到零，**压力主要来自"冷启动唤醒"而非持续占用**。

**结论：存储与计算额度都不是瓶颈。** 真正要关注的是**冷启动延迟**（第十节）。

## 六、驱动与连接方式（决定代码怎么写）

### 6.1 硬约束：我们需要事务

项目文档要求提议执行时"检查版本 → 再验证 → 执行 → 记录结果"，批量操作要定义事务或部分失败策略——**这些必须落在数据库事务里**。因此驱动必须支持事务。

### 6.2 Drizzle 对 Neon 提供四种写法（官方指南归纳）

| 驱动 | 机制 | 事务支持 | 官方适用场景 |
|---|---|---|---|
| `drizzle-orm/neon-http` | HTTP | **仅单次非交互式事务**（官方：Querying over HTTP is faster for single, non-interactive transactions）| 简单查询、边缘环境 |
| `drizzle-orm/neon-serverless` | WebSocket | 支持 session / 交互式事务（官方：需要 session or interactive transaction support 时用它）| 需要事务的 serverless 场景 |
| `drizzle-orm/node-postgres` | 标准 TCP（`pg`）| 支持 | 传统服务端环境 |
| `drizzle-orm/postgres-js` | 标准 TCP（`postgres.js`）| 支持 | 同上 |

**官方还明确两点**：

- To use Neon from a **serverful** environment, you can use the **node-postgres** or **Postgres.js** drivers.
- 用 WebSocket 驱动时，若运行环境没有全局 `WebSocket`（**Node.js 就是这种情况**），需额外安装 `ws` + `bufferutil` 并配置 `neonConfig.webSocketConstructor`。

### 6.3 推荐与理由

**第一阶段推荐 `pg`（`drizzle-orm/node-postgres`）+ Neon 的池化连接串。**

1. **事务开箱可用**，不需要为 WebSocket 额外引入 `ws`/`bufferutil` 与构造函数配置——少一层可能与 serverless 环境冲突的机制。
2. 项目现有路由已统一 `export const runtime = "nodejs"`，`pg` 在 Node 运行时下是最成熟的路径。
3. 从 Neon 换到别的 Postgres（含 Netlify Database）时**只要换连接串**，代码不动——降低供应商绑定。

**代价与对策**：serverless 下每次冷启动可能新建连接池，连接数随实例数增长。对策是**必须使用 Neon 的池化连接串**（官方：使用池化连接串即启用 PgBouncer；`default_pool_size` 约为 `max_connections` 的 0.9 倍）。

**备选（若不希望依赖对外 TCP）**：改用 `drizzle-orm/neon-serverless`（WebSocket）或 `neon-http`（HTTPS）。**这两条都不需要 TCP 5432**，可绕开 U1；代价是 `neon-http` 不支持交互式事务（不适合我们的提议执行流程），`neon-serverless` 需额外配置 `ws`。

**关于 `postgres.js` 的两个已知坑**（官方原文）：

- Drizzle 官方提醒：`postgres.js` **默认使用 prepared statements**，This could be a potential issue in **AWS environments**——而 Netlify Functions 跑在 AWS 上。
- Drizzle 的 Supabase 指南明确：若使用 **transaction 池化模式**，必须**关闭 prepare**（`{ prepare: false }`），该模式不支持 prepared statements。

→ 综合起来，**`pg` 比 `postgres.js` 更适合我们这条链路**。

### 6.4 ⚠️ 同日追加核实后的修订（2026-10-10）

我在写 Phase C 之前又去核实了 Neon 的连接指南，**发现 6.3 的驱动建议需要修订**。原文证据（`neon.com/docs/connect/choose-connection`）：

> "For platforms like **Netlify Functions**, Deno Deploy, or Cloudflare Workers (without Hyperdrive), use the **Neon serverless driver** (`@neondatabase/serverless`). It connects over HTTP or WebSockets instead of TCP, reducing connection setup latency."

同一页的平台对照表：

| 环境 | Neon 官方推荐驱动 | 连接池 |
|---|---|---|
| Railway / Render / VPS / Docker | `pg` 或 `postgres.js` | 客户端或 Neon 池化 |
| **Netlify / Deno Deploy** | **`@neondatabase/serverless`** | N/A（驱动自带机制）|
| Cloudflare Workers | `@neondatabase/serverless` | N/A |

**这条官方指南同时回答了我上一轮标为 U1 的未知项**：Neon 认为 Netlify Functions 应当使用 serverless 驱动而不是 TCP 直连。

而且它把 serverless 驱动的两种传输讲得很清楚（原文）：

- **HTTP**："faster for single queries (~3 round trips vs. ~8 for TCP) and supports **non-interactive** transactions"
- **WebSocket**："maintains a persistent connection within a request. It supports **interactive transactions** and is **compatible with the `node-postgres` API (`Pool`, `Client`)**"

**修订后的结论**：

1. **默认驱动从 `pg`（TCP）改为 `@neondatabase/serverless`，传输选 WebSocket。**
   理由：该约束 3 要求"事务必须得到保证，不要为了适配不支持交互式事务的 HTTP 驱动而削弱数据一致性"——**HTTP 传输只支持非交互式事务，因此直接排除**；WebSocket 明确支持交互式事务。
2. **它同时满足该约束 2（保留驱动替换能力）**：WebSocket 驱动**兼容 `node-postgres` 的 `Pool`/`Client` API**，业务层的写法与 `pg` 一致；Drizzle 侧对应 `drizzle-orm/neon-serverless`，与 `drizzle-orm/node-postgres` 提供同一套查询 API。
3. **仍然保留 `pg` 作为可切换项**：只要把连接初始化收敛到一个工厂模块，将来若部署形态变成"长驻服务器"（VPS / 容器），改成 `pg` + 池化连接串即可，业务代码不动。

6.3 节保留在文档里作为决策过程记录，**但以本节结论为准**。

**额外核实到的两条事实**（原文见 `neon.com/docs/connect/choose-connection`）：

- 池化连接 "handle up to **10,000 concurrent client connections**"；直连受 `max_connections` 限制，**约 100–4000**，取决于计算规格。
- 使用 WebSocket 驱动时若运行环境无全局 `WebSocket`（Node.js 即如此），需装 `ws` + `bufferutil` 并配置构造函数。

## 八、迁移、备份与回滚

### 8.1 迁移工具

采用 **Drizzle Kit**：以 Drizzle Schema（TypeScript）作为代码中的模型定义；`drizzle-kit generate` 生成迁移文件，`drizzle-kit migrate` 应用；**迁移文件进 Git**，可审查、可回溯。

| 项目文档的要求 | 对照 |
|---|---|
| 生产环境结构变更走迁移流程 | ✅ 用迁移文件，不在业务请求里 `CREATE/ALTER` |
| 不在普通请求里自动执行破坏性 Schema 修改 | ✅ 迁移只在发布流程执行 |
| 避免 Schema / 迁移文件 / 实际库结构长期不一致 | ✅ 单一来源（Drizzle Schema）生成迁移，不手改数据库 |
| 在测试环境验证关键迁移 | ✅ 用 Neon 每项目 10 个分支的能力建独立测试分支，先跑迁移 |
| 若已有成熟迁移机制，先分析后整合，不要维护两套 | ⚠️ 本项目**没有任何迁移机制**，无冲突；但**旧的 `data/*.json` 读写不能与数据库访问长期并存**，需一次性切干净 |

### 8.2 备份与恢复

| 手段 | 性质 | 说明 |
|---|---|---|
| Neon 即时恢复 | **短期** | 免费窗口：最多 6 小时或 1 GB 数据变更 |
| Neon 快照 | 免费 1 个 | 可作为一个恢复锚点 |
| `pg_dump` 定期导出 | **推荐主力** | 与供应商无关，导出的 SQL 可存任意位置；**唯一"换家也能带走"的保障** |
| 迁移文件 + Schema | 结构保障 | 结构可从代码重建，数据靠 `pg_dump` |

**结论**：免费额度提供的恢复能力偏"应急"，**不能替代备份**。建议 Phase H 增加一个最小的"定期导出"机制（哪怕是本地手动执行一次 `pg_dump` 并保存产物）。

### 8.3 迁移成本评估

- **数据搬迁成本：几乎为零**。当前没有数据库、没有真实业务数据。
- **代码改造成本：中等**。新增 Drizzle Schema、迁移、数据访问层，并把 4 个 `*-storage.ts` 的调用点换成服务层——这与 Phase C/D 的架构工作重叠，不是额外开销。
- **回滚方式**：因为是"从零建库"，回滚 = 还原到上一个部署（Netlify 支持回退历史部署）+ 在分支上保留旧 JSON 实现做对照，直到新实现通过验收。

| `DATABASE_URL` | 池化连接串（Neon 池化端点）| 生产 |
| `DATABASE_URL_UNPOOLED` | 直连串（**迁移专用**）| 生产/本地 |
| `DEFAULT_OWNER_ID` | 演示期隐式单用户的服务端标识 | 生产/本地 |
| `DEEPSEEK_*` | 现有 4 个变量 | 生产/本地 |

> "迁移走直连"这一点现升级为**【已验证事实】**（2026-10-10 补充核实）：Neon 官方文档的「pooled vs direct」对照表明确写着——**schema migrations、pg_dump/pg_restore、logical replication 用直连（direct）；应用流量用池化（pooled）**。并指出"对池化连接跑迁移可能失败，且报错不会明说是池化问题"。来源：`neon.com/docs/connect/connection-pooling` 及 `neon-postgres` 技能。

### 9.2 本地开发

- 本地**不连生产库**。二选一：用 Neon 的**免费项目分支**建开发分支；或本地起一个 Postgres 容器。
- `.env.example` 只放占位符，**真实连接串永不进仓库**。

### 9.3 禁止项（对照项目文档）

- 不提交真实凭据到 Git；
- 不在前端代码或公开 API 响应里暴露连接信息；
- 不把连接串写进 `schema.md`、README 或 Agent 提示词；
- 日志不打印完整连接串。
