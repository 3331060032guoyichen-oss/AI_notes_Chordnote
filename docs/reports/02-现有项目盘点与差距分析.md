## 4. 数据模型、API 与前端的现状细节

### 4.1 数据模型现状（与 `DATA_MODEL.md` 核对一致）

```
Raw            { id, text(≤50000), createdAt }                        ← 不可变，无 PATCH
Knowledge      { id, rawId, title, summary, content,
                 keyPoints[], concepts[], keywords[],
                 createdAt, updatedAt }                                ← 可 PATCH
KnowledgeRelation { id, sourceId, targetId, type:"related", reason, createdAt }  ← 无向、单类型
WikiPage       { id, title, kind(6种), summary, content, tags[],
                 parentId, sourceRawId, order, createdAt, updatedAt }  ← 只读
WikiLink       { id, sourceId, targetId, type(7种有向), reason }        ← 只读
```

**关键结构性问题：**

1. **`Knowledge` 没有标签字段。** 它有的是 `concepts[]` 和 `keywords[]`，两者语义重叠、无类型、无规范化、无别名。这是"标签体系"缺失的根因——不是缺 UI，是**缺数据模型**。
2. **`KnowledgeRelation` 无向。** 想做出链必须先改模型（加 `direction`，或引入有向 `Link` 实体）。
3. **`relations` 与 `wiki.links` 是两套并行的链接模型**，一套无向单类型、一套有向多类型，彼此不通用。这会造成"Wiki 里有类型的链接不能用在真实知识页上"的割裂。
4. **`Knowledge` 把"内容"和"元数据"混在一个扁平结构里**（summary/content/keyPoints/concepts/keywords），没有"原子化元数据"的边界。

## 5. 差距分析：哪些缺失最影响"笔记软件的完整性"

排序依据：**缺少它，用户是否还能完成"记下 → 找回 → 建立联系 → 复用"这条最基本的链条。** 能用替代方案绕过的排后面。

| 排序 | 差距 | 为什么它排这个位置 | 用户当下会怎么失败 |
|---|---|---|---|
| **1** | **Markdown 不渲染（也不解析）** | 笔记软件的内容层。现在所有内容都是纯文本，段落、列表、代码、引用、表格、图片全部表达不了。这不是"少个功能"，是**记录能力的天花板** | 想写一个带小标题和要点的知识页，只能写成一坨文字；粘贴公式/代码等于破坏排版 |
| **2** | **没有全文搜索** | 研究问题 A 的第二问"如何从一篇笔记找到相关知识"，答案的第一顺位就是搜索 | 知识页超过 20 张之后，只能靠肉眼在左侧列表里翻标题 |
| **3** | **关系是单向缺失的：没有出链、没有用户主动建链** | 产品核心叙事是"建立知识之间的联系"。目前用户**只能接受 AI 的建议**，不能自己决定"这两篇有关" | 用户发现两篇笔记相关 → 无处可点 → 只能等下一次 AI 整理时碰运气 |
| **4** | **反向链接面板没有（接口闲置）** | "别人引用了我"是知识网络存在感的一半，而且接口已经写好了 | 想知道"这个知识点被哪些笔记用到了"——无路可走 |
| **5** | **没有标签体系** | 研究问题 A 第三问：标签解决"多重归属"。缺它则主题索引、MOC 都无处依附 | 想做"我所有关于极限的笔记"——做不到 |
| **6** | **没有"未链接提及"（潜在关系发现）** | 知识网络从"有链接"到"能长大"的关键机制；也是 AI 最能增值的位置 | 库里明明有相关笔记，但永远不会被发现 |
| **7** | **图谱不可视化** | 它是"理解知识如何生长"的表达方式，但属于进阶能力——笔记少时信息量低 | 目前只能用文字列表看关系，看不出结构 |
| **8** | **数据层是本地 JSON 文件，且没有鉴权** | 与既定架构（云端 + 数据库 + 多设备）冲突，也让"多设备访问"无法成立 | 换台设备就看不到自己的笔记；部署到只读文件系统上写入会失败 |
| **9** | **没有"最近/回访"入口** | 研究问题 A 第六问"如何快速回到正在学习的内容"。它成本低但收益直接 | 每次都要重新找位置 |
| **10** | **没有 Proposal 中间态** | 影响的是"AI 建议的可追溯性"，现在有 Draft + 勾选的部分替代 | 一段时间后无法回答"这条关联是谁、什么时候、为什么建立的" |
| **11** | **AI 只有单轮问答、无上下文跟随** | 影响"长期记忆召回 / 跨多篇总结"这类差异化能力 | AI 每次都要用户手填上下文，且无法跨笔记 |
| **12** | 四类节点（Note/Question/Concept/Card）未实现、无别名机制 | 长期模型，属于产品演进方向 | 概念无法合并，同一概念会碎片化成多条 |

### 5.1 三个容易被误判的点（提醒，避免后续返工）

1. **"反向链接"不是从零做**：接口已存在且正确，缺的是**界面 + 有向关系模型**。
2. **"首次滑动边框 + 欢迎窗口"已经做完了**（`landing-page.tsx`），`ROADMAP.md` 的 C1/C2 应从待办中移除，`README.md` 需要更正。否则会重复开发。
3. **`components/` 不是空的**，`three` 已经在用。`AGENTS.md` 需要更正，否则 AI 编码工具可能重复造轮子或误用技术栈。
