## 二、逐条决策：差异与最小变更

### 决策 1 —— `note_revisions` 改为 RESTRICT

**差异**：`schema.ts` 第 72 行附近 `noteId: ... .references(() => notes.id, { onDelete: "cascade" })` → 改为 `"restrict"`。

**SQL 效果**：`ON DELETE cascade` → `ON DELETE restrict`（迁移中该 `ALTER TABLE "note_revisions" ADD CONSTRAINT ...` 一行）。

**与 07 文档的关系**：**不冲突，而是补齐**。§6.5 原文写的是"`note_revisions` 与 `audit_log` **保留**（审计需要）"，但没写**用什么机制**保留——RESTRICT 就是那个机制。文档需要补一句机制说明（列入待改文件）。

### 决策 2 —— `proposals` 改为 RESTRICT

**差异**：`targetNoteId: text("target_note_id").references(() => notes.id, { onDelete: "cascade" })` → `"restrict"`。

**注意**：该列**可空**，所以 `target_note_id IS NULL` 的提议不会阻挡删除；只有真正指向该笔记的提议才阻挡。这符合预期。

### 决策 3 —— 给枚举列加 CHECK：**只能部分执行，有阻塞项**

口径是"以代码和文档确认的合法值为准"。13 个枚举型列逐个对照了代码与 07 文档，结果是 **7 列可以立即加，3 列被词汇冲突阻塞，2 列根本没有值集可依**：

**✅ 可以直接加 CHECK（值集在代码与文档中一致）**

| 列 | 合法值 | 来源 |
|---|---|---|
| `notes.origin` | `user` / `ai` | schema 注释 + 07 §6.3（第 266 行）|
| `note_tags.origin` | `user` / `ai` | 同上（第 279 行）|
| `proposals.origin` | `ai` / `user` | 07 §6.3（第 306 行）|
| `proposals.kind` | `note_update` / `link_create` / `link_delete` / `note_merge` / `bulk_organize` / `moc_update` | 07 §6.3（第 301 行）|
| `proposals.status` | `pending` / `approved` / `rejected` / `applied` / `failed` / `stale` / `cancelled` | 07 §6.3（第 302 行）|
| `proposals.risk_level` | `low` / `medium` / `high` | 07 §6.3（第 304 行）|
| `audit_log.result` | `ok` / `failed` / `partial` | schema 注释 + 07 §6.3（第 313 行）|

**⚠️ 被"词汇冲突"阻塞的 3 列 —— 需要先裁决（见第三节 C1）**

`links.origin`（`user`/`agent`）、`note_revisions.author_type`（代码注释 `user`/`agent`/`system`，07 文档写 `user`/`agent`）、`audit_log.actor_type`（`user`/`agent`/`system`）。这三列用的是 **`agent`**，而 `notes.origin` / `note_tags.origin` / `proposals.origin` 用的是 **`ai`**。同一个语义角色有两套拼法，**没有唯一"已确认的合法值集"**，所以现在加 CHECK 等于我替你定标准。

**❌ 值集未定义的 2 列 —— 无法加 CHECK**

| 列 | 现状 | 问题 |
|---|---|---|
| `links.type` | schema 默认 `'related'`，**无枚举注释**；07 §6.3 写的是 `('related'\|'supports'\|'contains'\|'extends'\|**...**)` ← 开放式 | 代码侧**只接受 `related`**：`app/api/relations/route.ts:61` 明确 `if (body.type !== "related")` 报错；`types/relation.ts:5` 与 `types/graph.ts:11` 都写死 `type: "related"`。文档里的多类型来自**已删除的 Wiki 层**（`WikiLink`），那 7 种类型编码不同，不能直接搬。**合法集合没有定义** |
| `note_ai_metadata.status` | schema 默认 `'pending'`，注释只写"生成/审核状态" | 07 §6.3 与用户文档 §七.2 都**没有列出取值**。**合法集合没有定义** |

**建议**：`links.type` 暂时只用 `related` 建 CHECK（等链接类型设计定稿再用迁移扩展），`note_ai_metadata.status` 待值集确定。这两条都需要确认，我不擅自填。

### 决策 4 —— `notes` 索引暂缓：**零改动**

记录在案：保持现有 `notes_user_id_idx` + `notes_raw_id_idx`，等有真实查询计划和数据规模再评估复合索引。本文不做任何索引变更。

### 决策 5 —— `updated_at` 由服务层显式写入 + 补测试：**零 schema 改动**

现状：`created_at` / `updated_at` 都是 `timestamp with time zone NOT NULL DEFAULT now()`，**没有 ON UPDATE 触发器**（有意为之，避免隐式行为）。所以 schema 不需要动，需要的是**服务层纪律 + 测试**。

两点必须写进文档，否则实现时一定会踩：

1. 更新语句必须显式写 `updated_at`：`set updated_at = now()`。**漏写不会报错**——`DEFAULT` 只作用于 INSERT，UPDATE 时该列会静默保留旧值。这正是要用测试兜住的地方。
2. **`tags` 表没有 `updated_at` 列**。如果将来允许重命名标签，就没有时间戳可写。这是一个小缺口（当前白名单里 AI 不允许重命名标签），是否补列由你定。

### 决策 6 —— 归档优先 + 永久删除独立高风险流程：**有冲突，需要裁决**

**已具备的部分**：`notes.archived_at` 存在，与"归档优先"一致。

**冲突 1 —— `raw_notes` 没有归档字段。** `notes` 有 `archived_at`，`raw_notes` 没有（实测字段：`id / user_id / text / version / created_at / updated_at`）。而现有应用**对原始记录就是硬删除**：`app/api/raw/route.ts` 提供 `DELETE`，且被知识页引用时返回 409。如果决策 6 覆盖 `raw_notes`，那么"默认归档"目前无法执行——要么给它加 `archived_at`，要么明确决策 6 只针对 `notes`。

**冲突 2 —— `links` 仍然级联。** 外键 1、2 都是 `cascade`：删一篇笔记会**静默删掉它所有的正式关系**。决策 1、2 只保护了修订与提议，没保护关系。关系是"用户确认过的知识"，是否也算不该静默丢弃？需要你表态（我不擅自改）。

## 四、具体变更方案（待批准后再落地）

### 4.1 Schema 变更（`lib/db/schema.ts`）

```ts
// 决策 1
noteId: text("note_id").notNull()
  .references(() => notes.id, { onDelete: "restrict" }),      // was: cascade

// 决策 2
targetNoteId: text("target_note_id")
  .references(() => notes.id, { onDelete: "restrict" }),      // was: cascade

// 决策 3（示例：给 proposals.status 加 CHECK）
import { check } from "drizzle-orm/pg-core";
// ...表定义的第三个参数里追加：
statusCheck: check(
  "proposals_status_check",
  sql`"status" in ('pending','approved','rejected','applied','failed','stale','cancelled')`,
),
```

其余 6 个可立即添加的 CHECK：`notes_origin_check`、`note_tags_origin_check`、`proposals_origin_check`、`proposals_kind_check`、`proposals_risk_level_check`、`audit_log_result_check`。

**待裁决后才能决定是否添加的 CHECK**：`links_origin_check`、`note_revisions_author_type_check`、`audit_log_actor_type_check`（C1/C2）、`links_type_check`（C3）、`note_ai_metadata_status_check`（C4）。

### 4.2 迁移文件

两条路线，**推荐 A**：

| 路线 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A（推荐）重写 `0000`** | 改完 schema 后删除 `drizzle/` 下三个文件，重新 `drizzle-kit generate` | 得到一份干净、无已知缺陷的初始迁移；没有"修补迁移"的噪音 | 会替换掉现有 `0000` 文件（其 SHA256 已记录在本文第一节，可对照）；**前提是确认没有任何环境应用过 `0000`** |
| B 追加 `0001` | 保留 `0000`，新增 `ALTER` 迁移 | 不改写历史 | 初始迁移永久带着已知缺陷（cascade、缺 CHECK）|

### 4.3 是否涉及破坏性 SQL

**不涉及数据破坏。** 无论 A 还是 B：

- 重写的 `0000` 仍只会是 `CREATE TABLE` / `ALTER TABLE ADD CONSTRAINT` / `CREATE INDEX`，**没有任何 `DROP TABLE`、`DROP COLUMN`、`DELETE`、`TRUNCATE`、`ALTER COLUMN TYPE`**（现有 `0000` 实测为 0 条破坏性语句，改动后仍保持这种结构）。
- 改外键行为会生成 `ALTER TABLE ... DROP CONSTRAINT ... ; ADD CONSTRAINT ...` —— **`DROP CONSTRAINT` 只删约束、不动数据**，但会**短暂移除该外键的约束保护**（在同一迁移内的两条语句之间）。对新库无影响。
- 加 CHECK 约束**不会改数据**，但如果表里已存在不合规的行，`ADD CONSTRAINT` 会**直接失败**（这正是期望行为，不是静默清洗）。

### 4.4 回滚限制（必须提前知道）

- Drizzle Kit **没有自动 down 迁移**。回滚要么手写反向 SQL，要么依赖数据库快照。
- 因为 `0000` 是纯建表迁移，且目标库当前为空，**回滚成本极低**：删掉这 13 张表（含 `drizzle` schema 与 `__drizzle_migrations`）即可回到初始状态。**注意这是破坏性操作**，只能在 dev 分支做。
- 一旦往后有了真实数据，"删表回滚"就不再可行——那时回滚必须依赖备份（`pg_dump`）或 Neon 的即时恢复。

## 六、迁移前检查（执行前必做，均不触碰 production）

1. **确认 `0000` 从未被任何环境应用过**。dev 分支已实测 `public_tables = 0`（只读查询，非本次）；**production 从未连接、也不会连接** —— 需要所有者确认从未在那里执行过 `migrate`。若无法确认，就必须走路线 B（追加 `0001`）而不是重写 `0000`。
2. **确认当前指向 dev 分支**：`.neon` 的 `branch` 字段与 `.env.local` 的 `NEON_BRANCH` 都必须是 `dev`。
3. **迁移必须用直连串**（`DATABASE_URL_UNPOOLED`），不能用池化串。
4. 在 dev 上先 `drizzle-kit generate` 复核生成的 SQL 内容，再执行。

## 七、迁移后验证（在 dev 分支上）

**结构验证（SQL）**

1. 表数量：`select count(*) from information_schema.tables where table_schema = 'public'` → 期望 **13**（11 张业务表 + `__drizzle_migrations`；`drizzle` schema 在独立 schema 里不计数）
2. CHECK 约束存在：`select conname from pg_constraint where contype = 'c' and connamespace = 'public'::regnamespace` → 期望 7 条（或按最终裁决的数量）
3. 外键行为：`select conname, confdeltype from pg_constraint where contype = 'f'` → `note_revisions` 与 `proposals` 两条应为 `r`（restrict），其余按设计

**行为验证（负向测试，证明约束真的生效）**

- 插入 `proposals.status = 'bogus'` → **必须报错**（证明 CHECK 生效）
- 建一条 `raw_notes` + `notes` + 一条 `note_revisions`，然后 `delete from notes` → **必须报 FK 违例**（证明 RESTRICT 生效）
- 建一条引用该 `notes` 的 `proposals`，再删该笔记 → **必须报 FK 违例**
- 删一条**没有任何修订与提议**的笔记 → 应当成功（证明 RESTRICT 是精确的，不是一刀切禁止）
- 直接 `delete from audit_log` 不适用（无外键）——改为确认审计写入路径不受影响

**测试补强**

- 决策 5 要求：`update notes set title = ...` 之后断言 `updated_at` 变大；**故意不写 `updated_at`** 时断言测试失败（这是我们想要的守卫）。
- 项目当前**无测试框架**。按 Phase D 原计划引入（Vitest），上述断言落成用例。**迁移本身不做测试，只做上述 SQL 验证**。
