## 六、功能优先级（P0 / P1 / P2）

### 6.1 排序依据（先说清楚排序标准）

四个判据，按权重从高到低：

1. **它是否属于"笔记软件的基础能力"**（对照第一份报告 1.2 的分层表）。基础能力缺失会让产品在"能不能用"这一层就不成立。
2. **它是否阻塞其它功能**。例如数据层不改，后面所有功能都要返工一次。
3. **用户能否用现有能力绕过**。能绕过的降级处理。
4. **它是否服务于产品的差异化叙事**（生长式知识网络 + AI 提议）。

### 6.2 P0 —— 不做就不算笔记软件（建议先做这 5 项）

| # | 功能 | 为什么是 P0 | 现有基础 |
|---|---|---|---|
| **P0-1** | **数据层抽象 + 迁移到数据库** | **它是唯一一个"不先做，其它全白做"的项**。现在的存储是 `lib/*-storage.ts` 直接读写本地 JSON，与"云端 + 数据库 + 多设备"的既定架构冲突，且在只读文件系统上写入会失败。先抽出仓储接口，后续所有功能才有稳定的地基 | 5 个 storage 模块，接口已经比较整齐，改造成本可控 |
| **P0-2** | **Markdown 解析与渲染（先只做渲染）** | 内容层天花板。现在正文是纯文本，`reading-content` 里直接输出字符串，标题/列表/代码/引用/表格/图片全部表达不了 | 无任何基础，从零做 |
| **P0-3** | **全文搜索** | 研究问题 A 第二问的第一顺位答案。超过 20 张知识页后，用户只能肉眼翻标题 | 无 |
| **P0-4** | **有向链接（出链）** | 产品核心叙事是"建立知识之间的联系"，而当前 `KnowledgeRelation` 是无向、单类型，结构上无法表达"A 指向 B"，也无法让用户主动建链 | 需要改模型；`WikiLink` 已经有 7 种有向类型的现成设计可参考 |
| **P0-5** | **反向链接面板 + 标签体系** | 反向链接：**接口已写好但界面从未调用**，投入产出比最高的一项。标签：研究问题 A 第三问的"多重归属"，缺它则主题索引/MOC 无处依附 | 反向链接接口已存在；标签需要新增字段与聚合 |

**P0 的相对顺序建议**：`P0-1 → P0-2 → P0-4 → P0-5 → P0-3`。把搜索放在最后是因为它依赖数据层（索引），而它本身不阻塞别的功能。

### 6.3 P1 —— 让知识网络真正"长起来"

| # | 功能 | 理由 |
|---|---|---|
| P1-1 | **未链接提及 + 一键建链（AI 增强版）** | 第一份报告里最重要的发现。Obsidian 用纯字符串匹配做这件事，笨但有用；语言模型正好能把它升级为语义匹配。**这是 AI 与知识管理结合的最佳落点**，也直接复用你们"AI 只提议"的产品原则 |
| P1-2 | **图谱可视化（对标 Obsidian，先做局部图谱）** | **2026-10-10 决策：力导向图 + 可拖缩 + 筛选 + 节点大小∝被引用数**（见 `AGENTS.md` 的「决策记录」）。先做局部图谱（当前知识页的 1–2 层邻居）因为它永远可读、成本低；全库力导向图在大数据量下不可读（见第一份报告 3.4） |
| ~~P1-3~~ | ~~最近 / 回访入口~~ | **已取消（2026-10-10 决策）**：不做「最近」列表 |
| P1-4 | **命令面板 + 快捷键** | 功能变多之后，菜单不再是入口。现在是加它的最好时机——等到功能堆满再加，迁移成本更高 |
| P1-5 | **AI 面板改为"跟随当前笔记"** | 解决"AI 每次都要用户手填上下文"的结构问题，也是产品定位问题（见第三份报告 2.1）|
| P1-6 | **Proposal 实体（提议三态）** | 让 AI 建议可追溯。现在的"Draft 内建议 + 勾选"是部分替代，但无法回答"这条关联是谁、何时、为何建立的" |

### 7.2 数据实体（数据库设计提案）

**重要前提说明**：按约定先检查了现状——**当前项目没有任何数据库**，存储是 `lib/*-storage.ts` 读写 `data/*.json`。所以下面是"在现有实体之上补齐"的提案，**不是推翻重来**：现有 5 个实体的字段全部保留，只做增补与关系化。

建议 PostgreSQL（云 + 多设备 + 事务；本地开发可用同版本的 SQLite/Postgres 容器）。

```
-- 现有实体，字段保留，仅增补
raw        (id, text, created_at)
knowledge  (id, raw_id, title, summary, content,
            created_at, updated_at,
            + aliases   text[]      -- 别名（对应 Obsidian 的 aliases）
            + tags      text[]      -- 显式标签（与 concepts 分离）
            + search_vector tsvector)   -- 全文索引列

-- 链接：把现有"无向单类型 relation"升级为"有向多类型 link"
links      (id, source_id, target_id,
            type        text,        -- related | supports | contains | extends ...
            reason      text,
            origin      text,        -- 'user' | 'ai'   ← 关键：区分来源
            proposal_id uuid null,   -- 由哪条提议产生
            created_at, updated_at)
  index (source_id)            -- 出链查询
  index (target_id)            -- 入链查询
  unique (source_id, target_id, type)

-- 提议（Proposal）：AI 与用户的待决改动，三态
proposals  (id, kind,          -- link | knowledge_edit | knowledge_create | note_merge
            status,            -- proposed | accepted | rejected
            payload    jsonb,  -- 具体改动内容
            evidence   jsonb,  -- 依据（引用片段、来源笔记 id）
            origin     text,   -- 'ai' | 'user'
            created_at, resolved_at)

-- 标签字典（为聚合计数与重命名服务）
tags       (id, name, normalized_name unique, created_at)

-- 版本历史（P2-7）
revisions  (id, knowledge_id, content, summary, created_at, author) 
```

**迁移路径（对现有数据是安全的）**：

1. 现有 `KnowledgeRelation`（无向）迁为 `links` 中 **两行**（A→B 与 B→A，`type='related'`，`origin='user'`），保持行为等价——现在界面按无向显示，迁移后依然等价。
2. 现有 `concepts[]` 保持不动（不强行合并进 tags），只**新增** `tags[]`；两者分工在界面上说明（concepts = 概念，tags = 主题标签）。
3. `data/wiki.json` 的只读结构**保留在演示层**，不迁进主表（它是演示数据，不是用户数据）。

### 7.4 中文全文搜索的现实问题（这是最容易踩的坑）

必须提醒：**PostgreSQL 的全文检索对中文不友好**，它默认没有中文分词器。四个可行方案：

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| `pg_trgm` 三元组 + `ILIKE` | 无需分词器、托管 PG 都支持、对中文可用 | 无法做词干/相关性排序 | **P0-3 第一版就用它**，够用且零依赖 |
| PostgreSQL `tsvector` + 应用层分词 | 相关性排序好 | 需要维护分词、索引一致性 | 第二版可选 |
| `pg_jieba` / `zhparser` 扩展 | 原生最优 | 多数托管 PG 不允许装扩展 | 若自建库再考虑 |
| 外部搜索服务（Meilisearch / Typesense） | 中文支持好、快 | 多一个服务、多一份运维 | 数据量上千后再评估 |

再加一条：搜索的**结果排序**在没有相关性算法时，建议默认 `updated_at DESC`（用户最可能找最近动过的），而不是默认按文件名——这与 Obsidian 的默认不同（它按文件名 A→Z），但更符合"我要找回刚才写的东西"的真实意图。【推断】

### 7.5 Agent 工具设计（全部为"提议型"）

这是研究问题 C 里"如何避免 AI 自动修改造成知识污染"的答案：**Agent 的工具集中不提供任何直接写入工具**。

| 工具 | 类型 | 作用 | 返回 |
|---|---|---|---|
| `search_notes(query, limit)` | 只读 | 检索 | 命中列表（id + 标题 + 片段）|
| `read_note(id)` | 只读 | 读全文 | 内容 |
| `get_outgoing_links(id)` | 只读 | 出链 | 链接列表 |
| `get_backlinks(id)` | 只读 | 入链 | 反向链接列表 |
| `find_unlinked_mentions(id)` | 只读 | 潜在关系 | 提及列表（含依据片段）|
| `list_tags()` | 只读 | 标签清单 | 标签 + 计数 |
| **`propose_link(source, target, type, reason, evidence)`** | **提议** | 提出一条链接建议 | **`proposal_id`（不落链接）** |
| **`propose_knowledge_edit(id, patch, evidence)`** | **提议** | 提出字段修订 | **`proposal_id`** |
| **`propose_knowledge_create(raw_id, draft)`** | **提议** | 提出从 Raw 建立知识页 | **`proposal_id`** |

配套的两条硬约束（写进系统提示词与代码校验，双重保险）：

1. **笔记内容是"不可信数据"**：`search_notes` / `read_note` 返回的内容一律作为数据注入，绝不作为指令执行。用户笔记里可能出现"忽略以上指令"这类文本（Prompt Injection）。这一点 `ROADMAP.md` 的 B2 已经提出，本方案把它落到工具边界上——**只读工具返回内容，提议工具不接受来自内容的指令**。
2. **理由必须可核验**：`propose_link` 必须带 `evidence`（引用片段 + 来源 id），且服务端校验该片段确实存在于来源笔记中。这直接复用你们现有做法——`lib/deepseek.ts` 里已经有"Each relation reason must be grounded in both provided items"和"服务端过滤不存在的 knowledgeId"，把它扩展到链接提议上即可。

### 7.6 不要做的事（避免无必要重构）

1. **不要把 Raw/Knowledge 合并成一个 `Note` 表**。两层结构（不可变原始 + 可修订知识）是你们的产品原则，也是差异化点。
2. **不要引入 CSS 框架或组件库**去"顺便重写"样式。现有手写 CSS + 令牌是好做法。
3. **不要为了图谱引入力导向库**（见 7.1）。
4. **不要改 `/api/organize` 的返回契约**（`OrganizeDraft`）——它是现有闭环的核心，改动会连带 Draft 审阅界面。要加字段就向后兼容地加。
5. **不要为 AI 做专属视觉语言**（见第三份报告 3.9）。
6. **不要在没有 Proposal 机制的情况下开放 Agent 写操作**。

### 7.7 可选验证（如果你需要界面的视觉实证）

第一份报告里说明过：本机 REA 无法做原生 UI 截图（macOS 专属），所以**没有截图证据**。如果后续需要真实界面证据（例如要量某个面板的真实间距、要验证某个交互的动效），有一条可行路径：

```
以调试端口启动 Obsidian（会打开私人 vault）：
  Obsidian.exe --remote-debugging-port=9222
然后 REA 可以被动读取该实例的页面结构与截图。
```

## 八、分阶段实施计划

### 8.0 全阶段共同约定

- 每个阶段独立可验收、可回滚；阶段内不夹带其它阶段的内容。
- 每个阶段结束必须更新 `AGENTS.md` 的"当前已实现"与 `docs/ROADMAP.md`（把已完成的移出待办），避免再次出现第二份报告里那 7 条文档/代码不一致。
- 不新增路由；新增内容类型走 `Tab` 联合类型。

### 8.1 阶段划分

#### **Stage 0 —— 地基（P0-1 + P0-2）**

**范围**
1. 抽出仓储接口（`lib/repositories/*`），把 5 个 storage 模块收敛到统一接口后面；先保留 JSON 实现（行为不变，可回归验证），再新增数据库实现。
2. 建库、迁移脚本；`KnowledgeRelation` → `links`（两行有向、`origin='user'`）。
3. Markdown 渲染组件（只读渲染，不做编辑器）+ DOMPurify 消毒。
4. 新增排版令牌（第三份报告 3.1），替换正文相关硬编码样式。

**验收标准**
- 切换到数据库实现后，**现有 11 个接口的响应结构与行为完全不变**（用同一组请求对比前后响应）。
- 知识页正文支持：标题、段落、粗斜体、列表/任务列表、引用、行内代码、代码块、表格、图片、分割线、链接。
- 恶意内容用例被拦截：`<script>`、`onerror=`、`javascript:` 链接渲染后不产生可执行节点。
- 现有 JSON 数据能完整迁移，迁移前后条目数/字段逐条一致。

**测试方案**
- **单元测试（新建 vitest）**：`lib/*-storage` 双实现对照测试（同一输入，JSON 与 DB 输出一致）；Markdown 消毒用例集（≥ 10 条恶意样本）。
- **契约测试**：11 个接口的快照对比（迁移前录制 → 迁移后断言）。
- **手动走查**：现有 6 条路径（第三份报告 2.4 的 P1/P2/P6）逐一走通。

#### **Stage 1 —— 关系与检索（P0-4 + P0-5 + P0-3）**

**范围**
1. 有向链接：`links` 读写接口；正文 `[[` 自动补全 + 内联选择器（可复用现有 `@` 弹层）；指向不存在目标时生成"待建立"占位。
2. 右栏上下文面板：入链 / 出链两段（用上已存在但闲置的 backlinks 接口）。
3. 标签：`knowledge.tags[]`、标签聚合接口与标签页。
4. 搜索：`pg_trgm` 实现 + 搜索标签页 + 结果高亮 + 排序。

**验收标准**
- 在 A 页正文写 `[[B]]` 后：A 的"出链"出现 B；B 的"入链"出现 A 及引用片段。
- 指向不存在目标时：链接显示为"待建立"样式，且不报错；点击可创建。
- 搜索：中文关键词能命中（含正文中间位置的词）；结果高亮正确；无结果时给出下一步动作。
- 标签：某标签页列出全部相关条目，计数与列表一致。

**测试方案**
- 单元：链接解析（含 `[[A|别名]]`、`[[A#标题]]` 变体）、反向链接查询正确性（对称与有向两种数据的期望差异）。
- 集成：建链 → 查入链/出链 → 删链 → 复查（断言不残留）。
- E2E（Playwright）：P3、P4、P5 三条路径。

#### **Stage 2 —— 发现与俯瞰（P1-1 + P1-2 + P1-4）**

**范围**
1. 未链接提及：字符串匹配版（标题 + 别名），列表 + 一键建链。
2. 知识图谱：先做局部图谱（1–2 层邻居，力导向，可拖缩，点节点跳转），再做全库图谱（含筛选与分组着色）。
3. 命令面板 + 快捷键（第三份报告 3.8 的表）。

**验收标准**
- 未链接提及：正文出现某标题/别名但未建链时，右栏列出该条并可直接建立；建立后该条从列表消失。
- 图谱：局部图谱节点数 = 邻居数 + 1；可拖拽平移、滚轮缩放；**节点大小随被引用次数变化**（造两条入链验证）；点节点打开对应知识页；无邻居时显示空状态而不是空白画布。
- 命令面板：`Ctrl/Cmd+K` 打开；模糊匹配可用（如输入 `lt` 命中"留下原话"）；`Esc` 关闭。

**测试方案**
- 单元：提及扫描（含重叠匹配、同名词多处出现、别名匹配）；图谱邻居计算（含环形引用不死循环）。
- E2E：P4（含建立后消失）、P6。

#### **Stage 3 —— 提议与 AI 上下文（P1-5 + P1-6）**

**范围**
1. `proposals` 表 + 三态流转 + 接受/拒绝接口。
2. 把现有"AI 在 Draft 里提建议 + 勾选"升级为写入 `proposals`（保留现有交互外观，底层换实体）。
3. AI 面板改为跟随当前标签；`@` 保留为追加材料。
4. 提议的界面表达：**原始内容 / AI 建议 / 已写入内容三者必须在视觉上可区分**（研究问题 C 的最后一问）。

**验收标准**
- 每条 AI 建议可追溯到：来源材料、依据片段、生成时间、当前状态。
- 拒绝一条提议后，它不再出现在任何"待处理"位置，但**仍可查询到**（可追溯）。
- AI 面板跟随切换：从知识页 A 切到 B，面板上下文随之变为 B；`@` 追加其它材料仍生效。
- 视觉可区分：AI 建议使用与"已收录内容"明显不同的容器与标识（不是只加一个小图标）。

**测试方案**
- 单元：提议状态机（非法流转必须被拒：如 `rejected → accepted`）。
- 集成：提议 → 接受 → 链接入库 → 入链/出链同步更新。
- 人工验收：**视觉区分度**需要人工看一眼确认（这条无法自动化）。

#### **Stage 4 —— 差异化能力（P2）**

按需排：Concept + 别名 → 语义检索 → 跨笔记总结与长期记忆 → Agent 工具循环（必须在 Proposal 就绪后）→ 主题切换 / OCR / 剪藏。

**Stage 4 的验收必须单独设计**（依赖选型），此处不预设，等前三阶段完成后单独出一份方案。

### 8.2 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 现有文档与实际不符（7 条） | AI 编码工具会重复造轮子或误用技术栈 | **动手前先修文档**，这是 Stage 0 的第 0 步 |
| 无测试体系（当前无测试脚本） | 数据层迁移无法验证，回归全靠肉眼 | Stage 0 必须同时引入 vitest；先给现有 storage 补测试，再动迁移 |
| 中文全文搜索 | 方案选错会返工 | 先用 `pg_trgm`，把搜索实现藏在服务层后面，便于替换 |
| Markdown 渲染引入 XSS | 安全问题 | 渲染 + 消毒必须同时上线，不允许"先渲染后补消毒" |
| AI 写操作造成知识污染 | 违背产品原则 | 工具层不提供直接写接口；只提供 `propose_*`；理由必须可核验 |
| 落地页与工作台并存导致首屏成本高 | 性能与观感 | 现状已实现且设计文档有明确规范，本方案不动它；只在 Stage 2 检查 Three.js 场景在低端机上的帧率 |
| 一次性改动过大 | 难以定位回归 | 严格按阶段推进；每阶段结束跑一次全部既有路径的手动清单 |
