### 1.2 三条不可违背的原则（都来自项目文档）

1. **HTTP API 是统一业务入口**：前端、两种 MCP、内置 Agent 都调用同一套业务服务。**MCP 不得有自己的写库路径。**
2. **数据库是权威来源**：AI 的临时推理、总结、未批准的提议都不算正式数据。
3. **风控由服务端执行**：不依赖前端判断，也不依赖 Agent 自己遵守提示词。

## 二、各层职责与落点

> **【暂定决策】**：项目文档说"这是逻辑分层目标，不要求机械地创建对应数量的目录"。因此下面的"落点"以**最小改动形成清晰边界**为准，不新建一堆空目录。

| 层 | 职责 | 本项目落点 |
|---|---|---|
| 前端层 | 界面交互、调用 HTTP API | `app/page.tsx`（保持单页 + 标签页结构）|
| HTTP API 层 | 稳定的业务契约、参数校验入口、错误语义 | `app/api/**/route.ts`（**减薄**：只做解析、调用服务、映射错误）|
| 身份与授权层 | 构建用户上下文、资源归属检查、操作权限检查 | 新增 `lib/auth/context.ts` + `lib/auth/authorize.ts` |
| 业务服务层 | 笔记/标签/关系/AI 元数据/提议/审计的业务规则 | 新增 `lib/services/*.ts`（**核心新增**）|
| 数据访问层 | Drizzle Schema、查询、事务、连接工厂 | 新增 `lib/db/schema.ts`、`lib/db/client.ts`（连接工厂）、`drizzle/`（迁移）|
| MCP 接入层 | 两种传输的工具暴露与参数校验 | 新增 `mcp/`（stdio）与 `app/api/mcp/`（远程 HTTP）|
| 审计与恢复层 | 变更结果、版本、审计、幂等、备份 | 数据表 + `lib/services/audit.ts` + 备份脚本 |

### 2.1 关键约束：业务逻辑只允许存在一份

**【暂定决策】** 现在的 10 个 `route.ts` 把校验和业务规则写在一起。改造后：

- **路由处理器只允许做**：读取请求 → 调用服务 → 把服务结果/错误映射为 HTTP 响应。
- **服务层只允许做**：业务规则、事务边界、审计写入。
- **MCP 工具只允许做**：参数校验 + 调用**同一个**服务函数。

**验证方式（Phase D 的验收项）**：对同一业务动作（例如"创建笔记"），从 HTTP 与从 MCP 各调一次，**必须命中同一个服务函数**，且产生同构的审计记录。

## 三、两种 MCP 的调用路径

### 3.1 本地 stdio MCP

```
本地 Agent（Codex / Claude Code）
  → stdio MCP Server（本机进程）
    → 云端 HTTP API（HTTPS + 凭据）
      → 身份与授权层 → 业务服务层 → Drizzle → PostgreSQL
```

**【暂定决策】** 本地 MCP **不直连数据库**，一律走云端 HTTP API。理由：项目文档第三章第 3 条明确"不要默认让外部 Agent 直接连接数据库"，而走 API 可以让权限与校验天然生效。

**【暂定决策】** 凭据从**本机环境变量或本地配置文件**读取，**不进 Git**；`.gitignore` 需覆盖该配置路径。

**【已验证事实】** Node.js 环境默认没有全局 `WebSocket`（Neon 官方文档原文：需装 `ws` + `bufferutil` 并配置构造函数）——这条影响的是**服务端到数据库**的连接，与 MCP 的 stdio 传输无关，但同一个进程里都要处理好。

### 3.2 远程 HTTP MCP

```
远程 Agent → HTTPS MCP 入口 → 认证与授权 → 统一业务服务 → Drizzle → PostgreSQL
```

**【待部署验证】** 所采用的 MCP 传输规范的具体认证方式。约定是"遵循实际采用的 MCP 传输规范及其认证机制，不自行假设协议细节"——因此**在 Phase G 之前需要先核实该规范的当前版本与认证要求**，本文不编造协议细节。

**【暂定决策】** 远程 MCP 使用**可撤销、权限范围受限的令牌**（对应项目文档第五章第 3 条），令牌哈希后入库，**明文只在签发时返回一次**。

### 3.3 两种形态必须共享的东西

工具语义、参数校验、用户归属检查、白名单、提议与确认规则、错误格式、审计——全部共用同一套服务层。**差异只允许出现在传输、凭据来源、部署方式三处。**

## 四、用户归属与授权

### 4.1 演示期：隐式单用户

**【暂定决策】**

- 服务端用环境变量 `DEFAULT_OWNER_ID` 生成"当前用户上下文"。
- **浏览器或 Agent 传入的任何身份参数一律不被信任**（项目文档第三章第 3 条明令禁止）。
- 所有业务表都带 `user_id`，写入时由服务端上下文赋值。
- 所有查询、更新、删除都带 `user_id` 条件。

**【暂定决策】** 授权入口收敛成两个函数，**任何业务代码不得绕过**：

```
getUserContext(request)  → { userId, actorType: "user" | "agent", actorId }
assertCan(ctx, action, resource)  → 通过 / 抛授权错误
```

### 4.2 未来替换点

**【暂定决策】** 将来加登录时，只需把 `getUserContext` 的实现从"读环境变量"换成"校验会话/令牌"，**业务服务层不用改**。这就是项目文档要求的"不需要重写所有笔记业务逻辑"。

**【暂定决策】** 主体（actor）区分 `user` / `agent` / `system` 三类，并写进审计。**Agent 与用户在权限上是不同的主体**——这正是白名单机制生效的前提。

## 五、AI 自动执行白名单（字段级）

> 这是项目文档第六章的落地。三类操作（`user_edit` / `agent_auto_write` / `agent_proposal`）的**正式定义见 5.3**。

### 5.1 允许自动执行（无需提议）

| 操作 | 目标 | 允许的字段/范围 | 附加约束 |
|---|---|---|---|
| 搜索 / 读取 | notes / raw_notes / tags / links | 全部只读字段 | 仍须归属检查 |
| 生成总结、概念、相关推荐 | 仅返回，不落库 | — | 不写正式数据 |
| **创建新笔记** | notes | title / summary / content / 所属来源 | 不得指定已存在的 note id；不得覆盖；须标 `origin = 'ai'`；须带幂等键；服务端限数量与长度 |
| **补充标签** | tags / note_tags | 只**新增** `origin='ai'` 的标签关联 | **不得删除用户已有标签**；不得重命名；不得批量重构（超范围转提议）|
| **更新 AI 元数据** | note_ai_metadata | summary / concepts / keywords / classification / extracted_entities / status / model_name / source_version | **不得写 notes 与 raw_notes 的正文**；不得建立正式关系；不得跨用户 |

### 5.2 必须走提议（Agent 不得直接执行）

修改已有正文、覆盖标题、删除段落、**建立/删除正式关系**、合并笔记、修改/重构 MOC 与主题索引、批量整理、批量标签变更、任何可能覆盖用户最新修改的操作。

### 5.3 三类操作：`user_edit` / `agent_auto_write` / `agent_proposal`

> **【已确认决策 · 2026-10-10】** 本节由项目方确认，作为**正式架构约束**。
> 白名单与提议机制**只约束 Agent 发起的写入，不约束用户本人在产品界面中的正常编辑**。
> 三类操作必须分别定义权限与执行流程；**它们可以复用底层数据服务，但调用主体与授权规则不得混淆**。

#### A. `user_edit` —— 用户直接编辑

- **范围**：用户可以直接修改自己有权访问的笔记标题、正文、标签及其他允许编辑的字段。
- **不需要**创建提议，也**不需要**自我审批。
- **必须执行版本检查**：若笔记在编辑期间已发生变化，返回明确的冲突信息（`409 VERSION_CONFLICT`），**禁止静默覆盖**。
- **允许主体**：仅 `user`。

#### B. `agent_auto_write` —— Agent 白名单自动写入

- **范围**：创建新笔记、补充标签（仅新增）、更新独立 AI 元数据（`note_ai_metadata`）。
- **允许主体**：`agent` / `builtin_agent`（`user` 也可走这一类）。
- **仍需服务端校验**：字段白名单、归属、数量与长度限制、幂等。字段级约束见 5.1。

#### C. `agent_proposal` —— Agent 必须先提议

- **范围**：修改已有笔记正文或标题、建立或删除正式关系、合并笔记、修改 MOC、批量整理。完整清单见 5.2。
- **流程**：生成提议 → 用户审核 → 服务端重新校验（权限 + 归属 + 版本）→ 执行 → 记录结果。
- **允许主体**：`agent` / `builtin_agent`。

#### D. 高风险操作（三类共同受限）

删除、批量删除或覆盖、跨用户操作、系统级配置修改 → **必须显式确认 + 服务端权限校验**，且提供影响范围预览与恢复手段。

#### E. 三类的对照

| 类 | 定义 | 允许主体 | 是否需提议 | 版本检查 | 审计 |
|---|---|---|---|---|---|
| `user_edit` | 用户直接编辑自己的内容 | 仅 `user` | 否 | **必须** | 必须 |
| `agent_auto_write` | Agent 白名单内自动写入 | `agent` / `builtin_agent`（`user` 亦可）| 否 | 更新类**必须**；创建类不适用 | 必须 |
| `agent_proposal` | Agent 提议、用户批准后执行 | `agent` / `builtin_agent` | **必须** | **必须**（执行时重新校验）| 必须 |

#### F. 反绕过要求（**本决策的硬约束**）

1. **不能只在前端区分用户和 Agent。** 服务端必须自行识别操作主体、校验数据所有权与权限，并按调用来源强制执行相应规则。
2. **主体身份必须来自服务端的凭据 / 会话上下文**，**不得**来自请求体、查询参数或前端声明的字段。
3. **Agent 不得通过调用普通用户编辑接口来绕过提议机制**：`PATCH /api/notes/:id`、`PATCH /api/raw/:id` 属于 `user_edit`，**Agent 主体调用一律返回 `403 USE_PROPOSAL_FLOW`**，并在响应中指明应改用哪个提议工具。
4. 判定发生在**服务层**（见 5.4），因此 HTTP API、stdio MCP、远程 HTTP MCP **任一入口都无法绕过**。

### 5.4 权限判定的实现形态

**【暂定决策】** 用一张**服务端可维护、可测试的策略表**（纯 TypeScript 常量 + 判别函数）实现，不做权限管理后台。判定输入：主体类型、操作类型、目标资源、目标字段、影响范围。

**【已确认决策】** 判定发生在**服务层**，不是在路由里，也不是在 MCP 工具里——这样任何入口都绕不过。这条是 5.3F 能够成立的前提，不是可选项。

## 六、数据模型

### 6.1 与现有代码的映射（先说明，避免误判）

| 现有 TypeScript 类型 | 目标表 | 说明 |
|---|---|---|
| `Raw` | **`raw_notes`** | 原始记录。**用户可改、AI 不可改**（你此前的决策）|
| `Knowledge` | **`notes`** | 知识页（整理结果）|
| `KnowledgeRelation` | **`links`** | 由"无向单类型"升级为**有向多类型** |
| `OrganizeDraft` | 不落表 | 仍是服务端临时结构；确认后写入 `notes` |
| 无 | **`note_ai_metadata`** | 新增（你已指定独立表）|
| 无 | `note_revisions` / `proposals` / `audit_log` / `idempotency_keys` / `agent_tokens` / `tags` / `note_tags` | 新增 |

**【暂定决策】** 保留 `raw_notes` 与 `notes` 两张表（不合并成一张"笔记"表）。理由：你此前定下"Raw 用户可改、AI 不可改"的产品原则，需要原始出处与整理结果在**权限与可追溯性**上可区分。这与项目文档"不要未经分析就创建全部实体"的要求一致——它们是**既有的**两个概念，只是从 JSON 文件搬到数据库。

### 6.2 通用约定

**【暂定决策】** 所有业务表统一：

- 主键：`id text`（保留现有 `raw_` / `knowledge_` 前缀风格，便于与现有数据/日志对照）
- 归属：`user_id text not null`，并建索引
- 时间：`created_at timestamptz not null default now()`、`updated_at timestamptz`
- 版本：需要防覆盖的表带 `version integer not null default 1`

### 6.3 表设计草案

```
raw_notes
  id, user_id, text, version, archived_at, created_at, updated_at
        └ 原始记录。用户可改（走 PATCH + 版本检查）；AI 只读

notes
  id, user_id, raw_id → raw_notes.id, title, summary, content,
  key_points jsonb, concepts jsonb, keywords jsonb,   ← 用户确认后的结构化字段
  version, origin ('user' | 'ai'), archived_at, deleted_at, created_at, updated_at
        └ archived_at = 暂时收起（仍可见）；deleted_at = 墓碑（常规查询隐藏，可恢复）
        └ 知识页。正文/标题对 Agent 而言需走"提议"；结构化字段用户可直接编辑

note_revisions                       ← 版本历史（可追溯）
  id, note_id → notes.id, user_id, version, title, summary, content,
  author_type ('user'|'agent'|'system'), author_id, proposal_id, created_at

tags
  id, user_id, name, normalized_name, created_at
  unique (user_id, normalized_name)

note_tags
  note_id → notes.id, tag_id → tags.id,
  origin ('user' | 'ai'), created_at
  primary key (note_id, tag_id)
        └ origin 让"AI 补的标签"与"用户自己加的"可区分，且 AI 只能新增

links                                ← 正式关系（有向、多类型）
  id, user_id, source_note_id → notes.id, target_note_id → notes.id,
  type ('related'), reason,          ← 当前只允许 related；扩展需另开迁移
  origin ('user'|'ai'), proposal_id, deleted_at, created_at
  unique (user_id, source_note_id, target_note_id, type)
        └ 候选关系不进这张表，只存在于 proposals 里
        └ 普通删除 = 软删除（deleted_at），常规查询隐藏；重新建立同一关系须复活已有行

note_ai_metadata                     ← 你指定的独立表
  id, note_id → notes.id, user_id,
  ai_summary text,                    ← AI 生成的候选摘要（与 notes.summary 语义区分）
  candidate_concepts jsonb, candidate_keywords jsonb,
  extracted_entities jsonb, classification text,
  status text (暂无 CHECK：值集待确认), model_name text, source_version integer,
  created_at, updated_at
  unique (note_id)                   -- 一对一；理由见 6.4

proposals
  id, user_id,
  kind ('note_update'|'link_create'|'link_delete'|'note_merge'|'bulk_organize'|'moc_update'),
  status ('pending'|'approved'|'rejected'|'applied'|'failed'|'stale'|'cancelled'),
  target_note_id, payload jsonb, diff jsonb, reason text,
  impact jsonb, risk_level ('low'|'medium'|'high'),
  base_version integer,              -- 生成时所依据的笔记版本 ← 防静默覆盖的关键
  origin ('ai'|'user'), agent_id,
  result jsonb, created_at, resolved_at, applied_at

audit_log
  id, user_id, actor_type ('user'|'agent'|'system'), actor_id,
  operation, target_type, target_id, proposal_id,
  idempotency_key, result ('ok'|'failed'|'partial'),
  detail jsonb, created_at

idempotency_keys
  key, user_id, operation, request_hash, response_json, created_at
  primary key (user_id, key)

agent_tokens                         ← 远程 MCP 凭据（可撤销）
  id, user_id, name, token_hash, scopes jsonb,
  created_at, last_used_at, revoked_at
```

> **【已确认决策 · 落地时明确】** `note_ai_metadata` 的字段命名在实现时做了澄清：**用户确认后的 `summary` / `concepts` / `keywords` 留在 `notes` 表**（它们是正式内容、用户可编辑、Agent 改它们要走提议）；AI 的**候选层**才进 `note_ai_metadata`，并且为了不与 `notes` 同名字段混淆，命名为 `ai_summary` / `candidate_concepts` / `candidate_keywords`。这符合项目文档第七章第 2 节"最终应结合现有模型确定字段"的授权，也让"AI 元数据与正文在结构上分离"更彻底。

### 6.4 两个需要明确的设计选择

**【暂定决策】** `note_ai_metadata` 采用**一对一**（`note_id` 唯一约束）。

理由：项目文档第七章第 3 条给了两个选项，并说"不要仅为未来可能需要就引入复杂的版本体系"。一对一最省事；若将来需要保留多模型/多历史结果，再改成一对多（加 `model_name` 维度即可），迁移成本可控。

**【暂定决策】** `concepts` / `keywords` / `extracted_entities` 用 `jsonb`。理由：项目文档第七章第 4 条明确"对摘要、关键词和候选概念等适合整体读取的信息，可以根据 PostgreSQL 能力和项目需求使用 JSON/JSONB"。同时保留一句约束：**如果将来需要对概念做频繁过滤、独立索引或审核，再拆出独立的概念表**，不因用了 jsonb 就放弃合理约束。

### 6.5 删除与归档策略（2026-10-10 已确认）

**三个必须区分的语义**

| 语义 | 含义 | 谁能做 | 数据效果 |
|---|---|---|---|
| **归档 archive** | 从常规视图收起，数据完整保留 | 普通业务 API（用户）| 写 `archived_at`，不删任何行 |
| **软删除 soft-delete** | 墓碑式删除：常规查询隐藏，可恢复 | 普通业务 API（用户）| 写 `deleted_at`，**不删任何行** |
| **恢复 restore** | 取消归档或墓碑 | 普通业务 API（用户）| 清空 `archived_at` / `deleted_at` |
| **永久清除 purge** | 真正抹除数据 | **仅独立高风险流程**，需显式授权 + 审计 | 显式删除多张表的行；**另行设计** |

**普通业务 API 只做三种状态变更：archive（收起）/ soft-delete（墓碑）/ restore（恢复），一律不做物理删除。**

现状提醒：`DELETE /api/raw` 目前是**硬删除**（被知识页引用时返回 409）。按项目决策，**暂不修改旧的 JSON 存储层**，它随数据库存储层重写一起改成归档 / 墓碑机制。

**外键策略（已落实到 `0001` 迁移）**

| 外键 | 行为 | 理由 |
|---|---|---|
| `note_revisions.note_id → notes.id` | **RESTRICT** | 删笔记不得带走修订历史 |
| `proposals.target_note_id → notes.id` | **RESTRICT** | 删笔记不得带走提议历史 |
| `links.source_note_id / target_note_id → notes.id` | **RESTRICT** | 删笔记不得静默清掉已确认的正式关系 |
| `note_ai_metadata.note_id → notes.id` | CASCADE（不变）| 派生数据，可随笔记消失 |
| `note_tags.note_id → notes.id` | CASCADE（不变）| 关联行 |
| `notes.raw_id → raw_notes.id` | RESTRICT（原有）| 被知识页引用的原始记录不可删 |
| `audit_log` | **无任何外键** | 任何级联都影响不到审计 |

**为什么 RESTRICT 是"机制"而不是"解决"**

> **关于 `links` 的普通删除（2026-10-10 决策）**：关系删除改为**可恢复软删除**（`links.deleted_at`），常规查询隐藏已删除关系（过滤 `deleted_at is null`）。注意 `links_pair_idx` 是**完整唯一索引、不是部分索引**，所以重新建立同一关系时必须**复活已有行**（清空 `deleted_at`），不能插入新行。完整设计见 `10-purge永久清除设计.md`。

RESTRICT 只保证"不会被静默带走"。它带来一个必然结果：**笔记创建时就会写入 v1 修订**（事务 T1），因此加上 RESTRICT 之后，**任何笔记都无法被物理删除**，除非先显式处理它的修订、提议与正式关系。这不是 bug，是这套决策的直接后果，实现阶段不要误判。

**已确认设计：墓碑式软删（2026-10-10 决策）**

物理删除笔记 ⟹ 指向它的历史行必然悬空，因此**物理删除不作为常规路径**。

- `notes.deleted_at` 是墓碑标记；**常规查询一律排除 `deleted_at is not null`**（服务层职责，schema 不强制）。
- 打墓碑时**保留**：笔记行本身、`note_revisions` 全部修订、`proposals` 全部提议、`links` 两端正式关系、以及 `audit_log` 审计链。外键是 RESTRICT，本身就不允许它们被带走。
- **恢复能力纳入设计**：恢复 = 清空 `deleted_at`，笔记与其修订 / 提议 / 关系即重新可见。`archived_at`（收起）与 `deleted_at`（墓碑）是**两个独立状态**，可分别设置与清除。
- **两个必须由服务层处理的细节**：
  1. 关系查询也要过滤指向已删除笔记的行，否则会出现"指向不可见笔记的关系"。
  2. 打墓碑必须写审计（谁、何时、通过哪个入口）。

**永久清除（purge）另行设计，不在本次范围**

需要真正抹除数据时（合规要求、误建数据），必须走**独立高风险流程**：

- 显式授权 + 单独确认，**不复用普通删除接口**；
- 在**单个事务**内按固定顺序显式删除：`links → note_tags → note_ai_metadata → note_revisions → proposals → notes`；
- 在 `audit_log` 写一条记录（保存被删对象的 id 与标题快照——`audit_log` 无外键，该记录会存活）；
- **明确列出会被一并抹除的历史**，不得靠外键级联静默完成。

该流程的**完整设计已单独输出**：见 `10-purge永久清除设计.md`——含四类语义与权限边界、各关联表的处理方式、固定的事务顺序、审计 manifest 字段、幂等与并发策略、13 条测试用例，以及"零新迁移"的结论（前提是不给 Agent 增加提议类型）。其中仍有待确认项（是否两步走、是否必填原因、Agent 是否有删除路径等），确认后再实施。

## 七、变更提议：流程与状态机

### 7.1 流程

```
读取与分析（不写正式数据）
   → 提交提议（proposals.status = pending，记录 base_version）
     → 用户确认（approved / rejected）
       → 执行：重新验证权限 → 检查归属 → 检查版本 → 条件更新 → 写 revision → 写审计
         → applied（或 failed / stale）
```

**【暂定决策】** 白名单内的操作走"直接执行"路径，但**同样经过服务端权限与字段校验**，并写审计。

### 7.2 状态机（合法转换）

```
pending ──approve──→ approved ──apply 成功──→ applied
   │                    │
   │                    ├──apply 失败────────→ failed
   │                    └──版本已变──────────→ stale
   ├──reject──→ rejected
   └──cancel──→ cancelled
```

**【暂定决策】** 明确这些非法转换必须被服务端拒绝：

- `applied` / `rejected` / `cancelled` **不得**再回到 `pending`
- `stale` 只能"重新生成新提议"，**不得**直接 apply
- `applied` **不得**因重试再次执行（靠幂等键 + 状态检查双保险）

### 7.3 防静默覆盖（项目文档第八章第 3 节）

**【暂定决策】**

1. 提议创建时记录 `base_version = notes.version`。
2. 执行时用**条件更新**：`UPDATE notes SET ... , version = version + 1 WHERE id = $1 AND user_id = $2 AND version = $3`。
3. 若受影响行数为 **0**，说明用户已改过 → **回滚事务**，把提议置为 `stale`，返回明确错误码。
4. 每次成功写入前，把**旧内容**写进 `note_revisions`。

**这套做法不依赖 Neon 专有功能**，是标准 PostgreSQL 的条件更新 + 事务。

## 八、事务边界（该约束 3）

**【暂定决策】** 以下操作**必须**在单个数据库事务内完成；任一步失败则整体回滚：

| # | 操作 | 事务内必须完成的事 |
|---|---|---|
| T1 | 创建笔记 | 插入 `notes` → 插入 `note_revisions`（v1）→ 写 `audit_log` |
| T2 | 用户修改笔记正文 | 读当前版本 → 条件更新 `notes` → 插入 `note_revisions` → 写审计 |
| T3 | **接受并执行提议** | 校验归属 → 校验状态与版本 → 条件更新目标 → 写 revision → 更新提议状态为 applied → 写审计 |
| T4 | 建立/删除正式关系 | 校验两端归属与存在 → 写/删 `links` → 更新提议状态 → 写审计 |
| T5 | 补充标签 | upsert `tags` → 插入 `note_tags`（**只新增**）→ 写审计 |
| T6 | 更新 AI 元数据 | upsert `note_ai_metadata` → 写审计 |
| T7 | 批量整理 | **逐项条件更新**；策略见下 |

**T7 的策略（项目文档第八章/第十一章要求"准确报告部分失败"）：**

**【暂定决策】** 批量操作**默认整个批量在一个事务内**，任一目标版本冲突则整体回滚并把相关提议标 `stale`——这最安全，且避免"部分成功"的语义混乱。

若将来批量规模变大导致长事务，再改为"分批事务 + 逐项结果记录（成功/失败/跳过）"，**但必须显式实现，不得默认假装全部成功**。

**【暂定决策】** 明确不使用 `drizzle-orm/neon-http`：官方文档说明它只支持 **non-interactive transactions**，无法满足 T3/T7 的交互式多步事务。这与该约束 3 直接冲突，因此排除。

## 十、独立备份机制（该约束 5）

### 10.1 已核实的能力

**【已验证事实】**（`neon.com/docs/postgres/backup-restore/*`，2026-10-10）：

- Neon 内置 **instant restore / PITR**；官方原文："automatically retain a history of changes, **ranging from 1 day up to 30 days, depending on your Neon plan**"。
- Neon **明确支持标准 `pg_dump` / `pg_restore` 工作流**，并**官方提供两段式指南**：建 S3 桶 → 用 **GitHub Actions 每夜自动跑 `pg_dump`**，并**配置保留策略**（多久后删除备份）。
- 另有从其他 Postgres 迁移的 `pg_dump` / `pg_restore` 指南。

> ⚠️ **一处官方文档间的表述差异（如实标注）**：定价页在免费计划一栏写的是即时恢复窗口"**最多 6 小时或 1 GB 数据变更**"，而备份页写的是"**1 天到 30 天，取决于套餐**"。两者口径不一致，**免费计划的确切窗口需要在控制台确认**。这属于【待部署验证】。

### 10.2 备份设计（不依赖 Neon 专有功能）

**【暂定决策】**

| 项 | 设计 |
|---|---|
| 工具 | `pg_dump`（标准 PostgreSQL 工具）+ `pg_restore` |
| 频率 | 演示期每天一次；重要演示前手动再导一次 |
| 产物 | 自定义格式 dump（`-Fc`），可选择性恢复单表 |
| 异地存储 | 对象存储桶（S3 兼容）。**不放在 Netlify、也不放在 Neon** |
| 保留策略 | 保留最近 7 份每日 + 4 份每周（演示规模下体积可忽略）|
| 恢复测试 | **每个阶段至少做一次真实恢复演练**：把 dump 恢复到独立分支/本地库，跑一次读写验证 |
| 可迁移性 | 因为只用标准 `pg_dump`/`pg_restore` 与标准 SQL，**可原样恢复到任何 PostgreSQL 服务** |
| 不依赖什么 | 不使用 Neon 专有的分支/快照机制作为**唯一**备份手段（它们可作补充）|

**【待部署验证】** 备份脚本在 Netlify 之外的执行位置（本地 / GitHub Actions / 其它 CI）。项目文档要求异地存储，因此**不应把备份任务放在应用运行时**。
