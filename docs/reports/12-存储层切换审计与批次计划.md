## 三、批次计划（4 批，每批可独立验证）

> 分批原则：**先读后写、先被依赖者后依赖者**；每批结束时该批涉及的路由必须全部切换完成，**不允许留半切换状态**。

### B1 — 数据访问层 + 只读路径

- 新增 `lib/services/*` 与 Drizzle 数据访问（含"默认排除 `deleted_at`"的统一条件）
- 切换**只读**入口：`GET /api/raw`、`GET /api/knowledge`、`GET /api/knowledge/[id]`、`GET /api/knowledge/[id]/backlinks`、`GET /api/knowledge/[id]/relations`、`GET /api/relations`、`GET /api/graph`
- **同时**切换 #9 #10 两个 AI 端点的**读依赖**（它们只读，不写）
- 验收：空库下这些 GET 返回**与现在一致的形状**（空数组 / 空对象）；`tsc` 通过；页面能打开

### B2 — 原始记录写路径

- `POST /api/raw` → `sources.create`；`DELETE /api/raw` → **归档**（不再是硬删除）
- 验收：创建后能读回；归档后不出现在默认列表；被知识页引用时的保护仍然生效（现在是 409，改后按归档语义，需与 `notes.raw_id` 的 RESTRICT 呼应）

### B3 — 知识页写路径（决策 4）

- `POST /api/knowledge` → `notes.promoteFromSource`（**从原始记录手动提升**；同一 rawId 幂等，不重复建）
- `PATCH /api/knowledge/[id]` → `notes.update`（版本检查 + 写 `note_revisions`）
- 验收：提升 → 读回一致；重复提升不重复建；并发/过期版本返回 `409 VERSION_CONFLICT`

### B4 — 关系写路径 + 回归收尾

- `POST /api/relations` → `links.createOrRevive`（撞唯一索引走复活）；`DELETE /api/relations/[id]` → 软删
- 回填：`GET /api/knowledge/[id]/backlinks` 与 `/relations` 的入链/出链语义
- 验收：建链 → 出链/入链正确；软删后两边都隐藏；重建同一关系时**不报唯一约束错误**

## 四、⚠️ 验证阻塞点（必须先解决，否则"逐路由验证"无法进行）

**切换后要验证，需要一个已经建好表的数据库。而迁移目前尚未授权执行。**

三个可选路径：

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 先授权在 dev 执行迁移** | 最直接：dev 就是用来干这个的（`public_tables` 当前为 0） | 需要先复核 11 号文件的 SQL 并授权 |

| **C. 只做类型与静态验证** | `tsc` + 代码审查，不跑真实查询 | 无法验证真实 SQL 行为（CHECK、RESTRICT、事务），**不能宣称"已验证"** |

**建议：走 A**——dev 分支本来就是为这件事存在的，且库是空的、回滚成本极低。在授权前，我会先写 B1 的代码并做 `tsc` 级验证，**不宣称任何运行时验证通过**。

- `notes.raw_id` **保持 NOT NULL + RESTRICT**（实测确认），因此：**每篇知识页都必须来自一条原始记录**，通过"手动提升"创建。

## 七、备份与恢复能力核实（决策 3：优先用 Neon 现有能力，不自建）

**实测结论（2026-10-10）**：

| 项 | 值 | 来源 |
|---|---|---|
| 组织套餐 | **`free`** | `neon orgs list` 实测 |
| 项目历史窗口 | **`history_retention_seconds = 21600`**（正好 6 小时）| `neon projects get` 实测 |
| 免费套餐历史窗口默认 / 上限 | **6 小时 / 6 小时（历史总量上限 1 GB）** | 官方文档 *History window*，2026-10-10 抓取 |
| 该窗口覆盖的能力 | 即时恢复（PITR）、Time Travel 查询、从历史状态分支、快照 | 同上 |
| 计费 | 免费套餐该项**不收费**（限 1 GB）| 同上 |
| 窗口是否为 0 | 否。**若设为 0 会彻底关闭即时恢复与 Time Travel** | 同上 |
| 是否项目级 | 是，影响**所有分支** | 同上 |

**必须如实说明的三个后果**：

1. **误操作的可恢复窗口只有 6 小时。** 足以覆盖"刚删错就发现"，**不足以覆盖"昨天删错了"**。
2. **这与 purge 设计有直接冲突需要知晓**：purge 是物理抹除，而免费套餐下**没有超过 6 小时的内容级恢复手段**。也就是说 **purge 之后超过 6 小时就真的不可恢复**。这正是"二次确认 + 必填原因 + 审计留痕"必须存在的原因。
3. **升级套餐才能延长窗口**（Launch 上限 7 天、Scale 上限 30 天）——这是**成本决策**，不是技术决策，不替产品侧决定；在正式演示前值得再评估一次。

按该决策，**不搭建独立备份系统**。Neon 官方虽然支持 `pg_dump`，但那是"自建备份"，超出本轮范围。
