# 任务分发 · 线 ① 知识库与图谱（数据 · 检索 · 导出）

> 这份文件是**独立可开工**的。你不需要读另外两份分发文件。
> 但在写第一行代码之前，**必须先把 `AGENTS.md` 读完**——它是这个仓库唯一的权威入口，很多看起来"该这么做"的事在这个项目里是被明确禁止的。

## 你负责的这一条线是什么

**数据和后端**：数据库表结构、服务层、API 路由、检索、导出。简单说——**知识库本身怎么存、怎么查、怎么带走**。
你不做界面。界面上要展示什么，会有另外一条线（界面线）来消费你的接口。

## 开工前必须知道的事实

| 事实 | 说明 |
|---|---|
| 包管理器是 **pnpm** | **不要用 npm / yarn**，会破坏 lockfile 和 `node_modules` 结构 |
| 存储是 **Drizzle ORM + 本机 PGlite** | PostgreSQL 方言，跑在应用进程内，数据在 `data/pglite`。早就不是 JSON 文件了 |
| 枚举的**唯一来源**是 `lib/db/enums.ts` | 数据库 CHECK、TS 联合类型、服务层校验全部从它引用。**不要在两处各写一遍合法值** |
| 迁移在 `drizzle/`，编号到 `0005` | **追加新迁移，绝不重写已有的**。下一个是 `0006`。应用启动时会自动跑增量迁移，不需要手工执行 |
| 服务层是业务规则的唯一落点 | `lib/services/{sources,notes,links}.ts`。**归属过滤（`user_id`）必须写在服务层**，不要散在路由里 |
| API 路由在 `app/api/**/route.ts` | 每个都要 `export const runtime = "nodejs"` |
| 改完**必须 `git push`** | 交付物就是这份仓库，改动不推上去，别人拉下来就没有 |
| 验证命令 | `pnpm dev` 起服务后跑 `pnpm test`（回归测试，必须全绿）；`pnpm verify:db` 验证表结构 |
| 契约文档 | `docs/schema.md`——**只描述已实现状态**，没实现的标 `NOT IMPLEMENTED`。你实现完要更新它 |

## 红线（碰了会出事，这些是产品决策不是遗漏）

1. **不要重建「参考库 / Wiki」层**。它 2026-10-10 被整层删除，是主动决策。
2. **不要重建「今日学习 / 复习 / 知识检查」这三个视图**，也不要新增独立的复习/学习页面。（见 `docs/adr/0004`：错题只能作为一种 Source 进知识库，不能做成新视图。）
3. **AI 永远不能改写 `Source` 的正文**。用户能改（`PATCH /api/raw/:id`），Agent 主体会被 `requireUserActor()` 拒绝。
4. **AI 不能直接写 `Note`**。任何 AI 的写意图都必须走 `Proposal`（见 `docs/adr/0001`）。
5. **不要给 `Source` 加物理删除**。`archived_at`（收起）和 `deleted_at`（墓碑）是两个独立状态；purge 是另一套高风险流程。
6. **不要在模块顶层读环境变量**。`PGLITE_DATA_DIR` 与 `DEEPSEEK_API_KEY` 一律在函数内部读——顶层读取会把配置锁死在构建期。
7. **不要提交 `data/`**。本机库是使用者自己的数据（`.gitignore` 已挡住）；换机器就拷这个目录，或用知识包导出/导入。

## 任务清单

### A0 · Proposal 服务层与接口 —— 优先级 P0（**别人在等你**）
**为什么**：`proposals` 表、枚举、CHECK 约束、验证测试都已经存在，但**没有 service、没有路由、没有 TS 类型**。另外两条线（合并提议、Agent 工具循环）都卡在这上面，先做这个能解锁两个人。
**目标**：把 `Proposal` 变成真正可用的对象——创建、列表、接受、拒绝四件事。
**依赖**：无。
**交付物**：`lib/services/proposals.ts`、`types/proposal.ts`、`app/api/proposals/route.ts`（GET 列表 / POST 创建）、`app/api/proposals/[id]/route.ts`（PATCH 接受或拒绝）；把 `docs/schema.md` 里 `proposals` 的 `NOT IMPLEMENTED` 改掉。
**验收标准**：
- 三态流转正确：`proposed → accepted` / `proposed → rejected`，**已决议的 proposal 不能再被改状态**（返回 409）。
- 跨用户隔离：A 用户创建的 proposal，B 用户读不到、改不动（返回 404）。
- `pnpm test` 全绿，并为 proposal 新增至少 6 条断言（创建 / 列表 / 接受 / 拒绝 / 重复决议被拒 / 跨用户）。
**不要做**：不要在这个任务里实现"接受提案后自动落库"的各种副作用——那是提案**种类**的事，留给需要它的那条线。

### A1 · 错题作为一种 Source —— P1
**为什么**：错题创意的前提。`docs/adr/0004` 已经决定"错题是一条数据通路，不是新视图"。
**目标**：`Source` 能区分"随手记"和"错题"。
**依赖**：无。
**怎么做**：往 `raw_notes` 加一个 `kind` 列（枚举 `note | problem`，默认 `note`），枚举加进 `lib/db/enums.ts`，迁移用 `0005`，同时加 CHECK 约束。已有的行全部退化成 `note`。
**交付物**：迁移文件、schema、`lib/services/sources.ts` 的读写路径、`types/raw.ts`、`docs/schema.md` 更新。
**验收标准**：`pnpm verify:db` 显示新列可空/有 CHECK；插入非法枚举值被数据库拒绝（错误码 `23514`）；`pnpm test` 全绿 + 至少 4 条新断言（创建 problem / 默认值 / 非法值被拒 / 列表能按 kind 过滤）。
**不要做**：不要改 `notes` 表，也不要让错题能直接晋升成 `Note`。错题是通过 `Link` 指向已有知识页的。

### A2 · 全文检索 —— P1
**为什么**：知识库大了以后没有检索就是废的；它还是 A3（未链接提及）的前置。
**⚠️ 关键坑**：**Postgres 内置的 `tsvector` 对中文基本无效**——它按空格切词，而中文没有空格。`Nodum` 那类项目用 `tsvector + GIN` 能work是因为内容是英文。你们的内容是中文。
**怎么做**：用 **`pg_trgm` 三元组索引 + `ILIKE`**。建一个 GIN 索引覆盖标题与正文，查询用 `ILIKE '%关键词%'`。中文子串匹配这条路是能用的。注意本机跑的是 PGlite，扩展可用性要在动手前实测（`CREATE EXTENSION IF NOT EXISTS pg_trgm`），不通就退回应用侧过滤。
**依赖**：无。
**交付物**：迁移（`CREATE EXTENSION IF NOT EXISTS pg_trgm` + GIN 索引）、`lib/services/search.ts`、`app/api/search/route.ts`（GET，带 `q` 参数）、`docs/schema.md` 更新。
**验收标准**：中文关键词能命中正文内部的子串；返回结果必须**按 `user_id` 过滤**；结果里带足够的上下文片段供界面高亮；`pnpm test` 至少 5 条新断言（中文命中 / 无结果 / 跨用户不可见 / 空查询 / 超长查询）。
**不要做**：不要引入 Elasticsearch / Meilisearch 之类的外部服务——这是校赛项目，多一个服务就多一个部署会挂的地方。

### A3 · 未链接提及 —— P2
**为什么**：右栏四块设计里的一块（`AGENTS.md` 2026-10-10 决策）。它指的是"某条知识页的标题，出现在了另一条笔记的正文里，但两者之间没有 Link"。
**依赖**：**A2 必须先完成**（没有全文检索就做不了）。
**交付物**：`app/api/knowledge/[id]/unlinked-mentions/route.ts`；服务层查询。
**验收标准**：能找到"正文里出现了标题但无 Link"的候选；已经建过 Link 的不重复出现；跨用户不可见。
**不要做**：界面部分不归你（交给界面线）。

### A4 · 版本历史 —— P2
**为什么**：`note_revisions` 表已经在写（每次修改留一条），但**没有任何界面或接口能读它**。数据在，价值没兑现。
**依赖**：无。
**交付物**：`lib/services/revisions.ts`、`app/api/knowledge/[id]/revisions/route.ts`（GET 列表）、`app/api/knowledge/[id]/revisions/[revisionId]/route.ts`（GET 单条）。
**验收标准**：能按时间倒序列出某条知识页的全部修订；**恢复某一版时是"以该版为内容创建一条新修订"，绝不能删掉中间的修订**；跨用户隔离。
**不要做**：不要做物理删除修订的接口。

### A5 · OKF 知识包导出 —— P1
**为什么**：这是产品对外的**数据所有权承诺**（见 `docs/adr/0003`）——"数据永远是你的，可以整包带走"。
**格式规范**：`docs/adr/0002`。完整规范：<https://github.com/GoogleCloudPlatform/open-knowledge-format> 的 `SPEC.md`（Apache-2.0）。**只需读到 §9 即可**，§10（Attested Computation）与你们无关，不要实现。
**目标**：把整个知识库导出成一个 **OKF-conformant** 的目录树（或打包成 zip）。
**映射**：每条 `Note` → 一个 `.md` 文件，frontmatter 含 `type`（必填，用你们自己的概念类型名）、`title`、`description`、`generated`、`verified`、`status`、`sources`（来自对应的 `raw_notes`）；`Link` → 正文里的标准 markdown 链接；每个目录生成 `index.md`；顶层生成 `log.md`。
**依赖**：无。
**验收标准**：
- 导出目录满足 OKF §11 的 conformance 三条（每个 `.md` 有可解析 frontmatter、`type` 非空、`index.md`/`log.md` 结构正确）。
- `[[` 与 markdown 链接两种写法都要能解析成 bundle 内的相对路径。
- 导出**不做任何破坏性操作**，纯读。
- 用一条命令就能导出（比如 `pnpm export:okf`）。
**不要做**：不要实现导入（那是另一个任务）；不要为了导出改数据库结构；**不要在任何地方宣称"完整实现了 OKF"**，规范很宽松，你们只做到 conformant。

### A6 · 重复概念合并提议 —— P2
**为什么**：LLM Wiki 的 Lint 工作流。学生会写出"梯度下降"和"GD"两条知识页。
**依赖**：**A0 必须先完成**（提议要写进 `proposals` 表）。
**怎么找重复**：先用便宜的方法——标题归一化（去空格、大小写、全半角）后相同或一方包含另一方；再考虑用 embedding 相似度（`pgvector` 是可选扩展，PGlite 上要先验证可用）。**先做便宜的那一层**。
**交付物**：一个可重复运行的脚本或服务函数，扫描后**以 Proposal 形式**提出合并建议，不自动合并。
**验收标准**：能跑出一批候选；每一条都写进 `proposals` 且状态是 `proposed`；**绝不自动合并**；可重复运行不产生重复提议。
**不要做**：不要自动合并。用户在界面上确认才算数。
