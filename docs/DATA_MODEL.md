# Data Model

> 2026-10-12 重写。字段级权威定义是 [`schema.md`](schema.md)（PostgreSQL + Drizzle）。本文只讲**产品对象如何落在这些表上**，以及已定的模型决策。旧版中的 JSON 文件存储、Wiki、四类节点映射均已过时，已移除。

## 一、产品对象 ↔ 数据表

| 用户看到的 | 落在哪里 | 说明 |
|---|---|---|
| **笔记** | `notes`（Knowledge） | 唯一的一等对象。用户写、改、删的都是它 |
| 原始出处 | `raw_notes` | 笔记创建时的原文，幕后保留。界面不单独呈现，也不提供编辑入口（`PATCH /api/raw/:id` 保留，不删） |
| **链接** | `links` | **有向**：`source_note_id → target_note_id`；`type` 目前恒为 `related`；`reason` 必填 |
| 修订 / 撤销 | `note_revisions` | 每次笔记更新写完整快照 |
| 标签 / 课程 | `tags` + `note_tags` | 表已建，API 未做；"课程"将作为一种标签 |
| AI 建议 | **不持久化** | `OrganizeDraft`，由 `/api/organize` 临时返回，用户采用后才写入笔记字段 |
| 概念 | `notes.concepts`（jsonb 中保存的字符串数组）的聚合 | 派生，没有概念表 |
| 知识网络 | 派生 | `GET /api/graph` 从 `notes` + `links` 实时生成 |

## 二、派生视图（都不存储）

- **出链 / 反链**：按 `links` 的方向查询。反链需要带上 `reason`（选中的原文片段），接口以向后兼容的方式增加 `links` 字段。
- **未链接提及**：其他笔记的标题在当前正文中出现、但尚无链接。纯字符串匹配，不调 AI。
- **共同概念**：与当前笔记共享至少一个 `concepts` 的其他笔记。
- **孤立笔记**：既无出链也无反链。
- **成长计数**：笔记数 / 链接数 / 孤立数，来自 `/api/graph`。

## 三、已定模型决策

### 1. 一条笔记，不是两层

用户日常面对的只有"笔记"。新建笔记时，服务端在**一个事务**里创建 `raw_notes`（原文）和 `notes`（初始内容 = 原文），新增 `POST /api/notes { text }`，避免前端连发两次请求造成半成功。

> 2026-10-10 的"Raw 用户可改、AI 不可改"仍然成立，但 Raw 的编辑入口退出界面：用户改的是笔记，原文天然保留为出处。

### 2. 链接有方向，且无需迁移

`links` 的唯一索引本来就是 `(user_id, source_note_id, target_note_id, type)`，是有向的；"无序对去重"只是服务层规则。改成有序对去重即可。注意：

- 旧的回归断言"反向重复建链视为同一条"会失败，这是**预期内的行为变更**，改测试时要在提交说明里写明。
- AI 建议的链接，默认从"被整理的笔记"指向"建议的笔记"。
- 已被软删的链接，重建时仍然**复活原行**（唯一索引是完整索引）。

### 3. 笔记需要删除

当前只有 Raw 能归档，笔记没有删除接口，而阶段一要求"建立 / 删除 / 修改"。新增：

- `DELETE /api/knowledge/:id`：删除笔记；删除前必须经过明确的二次确认。
- 删除后的存储、恢复与永久清除接口，待实际实现时再单独确定。

删除后的查询表现与数据保留策略，待接口实现时一并定义；本轮产品规则只保留“删除前必须二次确认”。

### 4. AI 元数据暂不落库

`note_ai_metadata` 目前只有 `ai_summary`、`candidate_concepts`、`candidate_keywords`、`extracted_entities`、`classification`，没有要点和整理版正文的位置。第一版 AI 建议不存；每次保存后（或用户点"整理"时）临时生成。若以后要保留建议历史，再设计迁移。

### 5. `/api/organize` 需要读"当前笔记"

目前它按 `rawId` 读原文，用户改过笔记后原文就过期了。增加 `knowledgeId` 参数（与 `rawId` 二选一），按笔记的**当前内容**整理。提示词中附上已有概念名（按近期使用取前 50 个），让模型优先复用，避免"反向传播 / BP / 误差反传"各成一派。

### 6. 概念保持为字符串

不建概念表。点击概念标签 = 列出共享该概念的笔记。以后确需概念页，再把概念升级为 `kind='concept'` 的笔记。

## 四、jsonb 写入约定

`concepts` / `key_points` / `keywords` / `detail` 写入时直接传数组或对象，不要手动 `JSON.stringify`（详见 `schema.md` §1）。共同概念的查询依赖这一点：若库里存的是 jsonb 字符串值，`?` 与 `->` 全部失效。

## 五、长期想法（不排期）

- `Question` / `Card`：作为笔记的 `kind`，不新建体系。
- `Proposal`：当 AI 开始提出"跨笔记的批量改动"时再引入；现阶段"建议 → 点一下采用"已足够。
