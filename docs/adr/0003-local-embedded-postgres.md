# 知识库落到本机：PGlite 取代云 Postgres，可分享的网址退场

**这条取代原来的 0003「存储层不搬到本地」**。原决策针对的是「纯 Web 部署」这个前提：Netlify 的函数文件系统只读，写本地文件必然失败，所以存储只能上云，代价是「数据留在用户本机」这条做不到。现在前提变了——演示与日常使用都跑在本机，**可分享的网址让位给「数据在你自己的文件夹里」**。

**决定**：存储层换成 **PGlite**，也就是编译成 WebAssembly 的 PostgreSQL，跑在应用进程内，数据落在 `data/pglite`。**SQL 方言不变**，因此 `lib/db/schema.ts`、`drizzle/` 的六条迁移、五个服务层文件一行都没改——换掉的只有 `lib/db/client.ts` 这一个文件（连接工厂）。迁移在首次打开数据目录时自动补齐，使用者不需要知道有"迁移"这回事。

**为什么是 PGlite 而不是 SQLite 或 `data/*.json`**：

- 项目的并发口径（乐观并发用 `version` 比对、状态机用 `CHECK` 约束、关系去重靠 `links_pair_idx` 唯一索引、出处靠 `RESTRICT` 外键挡住删除）全部由 Postgres 语义承担。换 SQLite 等于把这些不变量在另一个方言里重写一遍，回归测试 75 条断言要重新推导。
- 写 JSON 文件则要把五个服务层的写入路径退化成"读全量、改内存、整体写回"，并发与崩溃后果都不可控。
- PGlite 让**所有现有 SQL 与迁移原样可用**，是唯一"零语义漂移"的本地化路径。

**后果**：

- 不再有 `DATABASE_URL`，也不再有 Neon 与 Netlify 相关的脚本与配置。
- **PGlite 是单写者**：同一份数据目录同一时刻只允许一个进程写。这条约束直接影响工具链——验证脚本不再连"正在被应用使用的那份库"（`pnpm verify:db` 改为在干净的内存库上跑迁移并验证结构与归属隔离），重置脚本则要求先停掉 `pnpm dev`。详见 AGENTS.md「已知坑」。
- 「数据是你的」现在可以直说：知识库就在本机 `data/` 目录，备份就是拷目录或者走「导出知识包」。但**不要**写成"多设备同步"或"云端不经过我们的服务器"之外的东西——数据不出本机，代价是换台机器要自己拷。
- 对外材料可以写：数据存本机、可完整导出、不被平台锁定。不要写"支持多端同步"。
