# Markdown 文件作为知识正文的权威来源，PGlite 降级为可重建索引

当前正文与元数据都在本机 PGlite 里（ADR-0003）。产品目标要求用户能用 Obsidian 与普通文件工具读写自己的知识，因此必须提前决定"谁是权威"，否则 Markdown 与数据库会变成两份互相竞争的真相。**本次只记录方向与迁移方案，不实施文件系统迁移。**

## 决定

**知识正文以 Markdown 文件为权威；PGlite 只保留两类数据：可重建的索引，以及不可重建但也不构成第二权威的应用记录。**

| 数据 | 权威位置 | 说明 |
|---|---|---|
| Source 正文与标题 | 文件（`raw/**/*.md`） | 用户与 AI 的分界不变：用户可改，AI 不可改 |
| Note 标题 / 摘要 / 正文 / 要点 / 概念 / 关键词 / 标签 | 文件 frontmatter 与正文 | 文件名不是身份，`id` 写在 frontmatter 里 |
| Link（存在与否、理由） | 文件 frontmatter 的链接列表 | 两侧 ID 稳定；关系语义仍按现有无序对处理 |
| 索引（按 id / 路径查找、全文检索、图谱投影、反向链接） | PGlite，可整表删除后重建 | 删掉不丢知识 |
| Proposal 与状态机、Note 修订历史、Audit、Idempotency、Agent 令牌 | PGlite，不可重建 | 它们是操作记录，不是知识正文；不参与"内容权威" |
| 模型配置与凭据 | `data/settings.json` | 见 ADR-0007 |

这条边界的意思是：**丢文件 = 丢知识；丢数据库 = 丢历史与索引，但知识还在。** 反过来，数据库永远不会把一份已被外部编辑过的文件覆盖回去。

## 外部修改、重命名与冲突

- 身份靠 frontmatter `id`，不靠路径。重命名 = 同一 id 的路径变化，更新索引中的路径，不新建 Note。
- 外部新增：扫描到没有 `id` 的文件，导入时分配 `note_*` / `raw_*` 并写回 frontmatter（一次写操作，先备份）。
- 外部删除：索引标记墓碑，不立即删修订与提议；用户可在应用内确认清除。
- 外部修改：以**文件内容哈希**判断变化。索引只读文件，不反向写文件。若某条 pending 提议的 `baseVersion` 所依据的内容已变，提议转为 `stale`（与现有状态机一致），而不是强行应用。
- 应用写入：先写临时文件再原子重命名；写前比对哈希，发现文件在本次编辑期间被外部改过就停下并提示，不静默覆盖。
- 已知风险：OneDrive / iCloud 同步冲突副本、CRLF、路径长度与大小写差异。迁移阶段必须逐项实测，不得假设。

## 索引重建与备份

重建 = 清空索引表 → 扫描权威目录 → 重新解析 frontmatter 与正文 → 重建图谱投影。它不需要网络，也不需要模型。备份 = 复制知识库目录；导出知识包仍保留，作为跨机器迁移形态。

## 迁移步骤（后续阶段，不在本次实施）

1. 冻结写入口：确认所有写路径都经过服务层。
2. 导出当前 PGlite 快照（JSON bundle）并留档。
3. 以只读方式把现有 Source / Note 写成 Markdown，记录 id 映射与内容哈希。
4. 逐条校验：数量一致、标题一致、正文哈希一致、链接两端都存在。
5. 切换权威开关，读路径改为文件 + 索引；写路径改为文件优先、索引跟随。
6. 保留旧数据库一个版本周期；回滚 = 切回权威开关，不丢数据。
7. 验收标准：外部编辑被索引到、重命名不产生重复页、删除可恢复、索引可从零重建、备份可完整恢复。

## 文件访问机制：三种方案的取舍

| 方案 | 结论 | 理由 |
|---|---|---|
| 浏览器 File System Access API | **不采用** | 目录句柄只在浏览器里。Agent 与索引都在服务端，拿不到句柄；要用它就得把 PGlite、服务层和模型调用整体搬到浏览器，密钥也会暴露在前端 |
| 本机文件服务（现有 Next 进程读写用户指定根目录） | **下一阶段采用** | 应用本来就跑在用户机器上，Node 有真实读写权限；成本最低。安全上必须固定根目录、拒绝请求传入任意路径、校验路径穿越与符号链接、写请求只接受本机来源 |
| 桌面容器（Tauri / Electron） | **备选** | 能提供系统级文件夹选择与权限隔离，但引入第二套运行时与打包链路，校赛阶段成本过高 |

本机文件服务不能靠"让用户填一个路径"就算完成授权：路径必须由用户显式确认一次并存入本机配置，之后所有读写都被限制在该根目录内。实现时须同时验证符号链接逃逸与 `..` 穿越。

## 后果

- 在迁移完成前，PGlite 仍是唯一权威；不得对外宣称"支持本地 Markdown 文件夹"。
- 现有的导出、导入、修订、提议状态机全部保留，迁移只换权威位置，不改业务规则。
- 这条决策难以回头（写路径、恢复流程、用户心智都会围绕它重建），因此先落纸再动代码。
